# Modules

## Curated modules

Clusters of resources that a curated public module can manage move into a call of that module, at an exact version. For each cluster, infraharvest maps the generated configuration onto the module's inputs. It declines a cluster when the module can't express one of its settings, rather than drop the setting. It then plans, and takes back any call whose resources would plan differently than they did in the root, or for which the module would create anything else. When the plan fails in a way it can't pin on one call, with an error about none of them or totals that don't match ("the plan changed outside the module calls"), it plans again with half of the calls, the others held back, and keeps halving until only the calls that cause it are declined, with that reason; the others stay. These extra plans are paid only when the plan fails. The root README and the report list each call, and each cluster that stayed in the root with the reason. These modules are mapped so far:

No Azure module is called yet. The one Azure adapter maps onto the Azure Verified Modules managed identity module, whose newest release, 0.5.3, accepts azurerm below 5 only, and a module version never holds the provider back a major release (see below): user-assigned identities and their federated credentials stay in the root as plain azurerm 5 resources, and the report says why. Azure Verified Modules for the other resources an Azure import lists can't be called either. The resource group, virtual network, network security group and storage account modules manage their resources through `azapi_resource`: imported into them, azapi plans an update of its own arguments (such as `retry` and `timeouts`) and of body properties the modules set to null, so they can't pass the zero-change check. The Key Vault, Log Analytics workspace, route table, public IP, network interface and virtual machine modules manage azurerm resources, but accept azurerm below 5 only. So an Azure import's clusters stay in the root, or move into a [generated local module](#generated-local-modules) where two or more in a root have the same shape. The identity adapter stays: once a release of the module accepts azurerm 5 and still manages `azurerm_user_assigned_identity`, the adapter is bumped to it, and `--modules latest-untested` calls it before then. A release that reaches azurerm 5 by moving to `azapi_resource`, as the modules above did, doesn't fit the adapter.

A call leaves out the arguments that are the module's own defaults, as a person calling it would: the network module's `mtu = 0` or `bgp_best_path_selection_mode = "LEGACY"`, the bucket module's `force_destroy = false`. For the AWS modules, that is a VPC's DNS support and hostnames, tenancy, usage metrics, subnet name suffixes, subnet names when the module would give the same, and public IP mapping; a bucket's force destroy, object lock, namespace, public access block settings, object ownership and MFA delete; a role's path, maximum session duration and tags. Two arguments stay at values the module doesn't default to, to keep the plan unchanged: the S3 module's `skip_destroy_public_access_block = null` (its default, `true`, would update the public access block in state), and the VPC module's `manage_default_route_table = false`, since the main route table AWS creates with a VPC, while unchanged, is left out (see [AWS](aws.md#what-the-default-selection-leaves-out)), and the module would otherwise adopt it and tag it. A role trusting GitHub Actions keeps its trust policy as `source_trust_policy_documents`: the module's `enable_github_oidc` writes a statement of its own (a `GithubOidcAuth` statement ID, `sts:TagSession` and an issuer condition), which a policy written by hand rarely matches, so the plan would update it.

Where the shared tags of a root are in `local.tags` and the VPC's resources set `merge(local.tags, { ... })` (see [Output](output.md)), the VPC call passes `tags = local.tags`, merged with the tags all of them set over it, and their other tags as the module's per-resource inputs, such as `private_subnet_tags`. A VPC whose resources don't all merge their tags over the same local stays in the root.

References to the resources a call takes use the module's outputs: `vpc_id = module.vpc.vpc_id`, `subnet_id = module.vpc.public_subnets[0]`. A list of every element of a list output becomes the output, `subnets = module.vpc.public_subnets`: in any order where the argument is a set, as a load balancer's `subnets` and an Auto Scaling group's `vpc_zone_identifier` are, and otherwise only in the output's order. A load balancer's `subnet_mapping` blocks that only name those subnets become `subnets` too. The change is kept only if a new plan shows no extra changes.

A module may set arguments the provider keeps only in state, such as the iam-role module's `force_detach_policies`. Import can't set those. The plan then updates them in state alone, and the verification gate lists those updates.

A module may use a provider besides the root's: the network module creates networks through `google-beta`, and Azure Verified Modules declare `azapi`. Only a root that keeps such a call requires and configures that provider, like its own (the same project, region and labels setting, or the same subscription and cloud) and pins it as it pins its own.

Each adapter pins an exact module version and is checked against that version's variables and outputs, its defaults against the defaults the variables declare, and the inputs its `Inverse` maps the module's resources' attributes onto, which `infraharvest drift` edits to accept a change of one of those resources into the call (see [Drift](drift.md#resources-in-module-calls)), against its variables and the resources the adapter maps onto. At import, the registry says whether a module has a newer release: the report names it, and `--modules latest-untested` calls the newest release instead of the tested one (the plan check still decides whether each call is kept). Nobody has reviewed those releases: `terraform init` downloads them and the plans run their code with the import's cloud credentials, so the import logs a warning saying so. Modules are trusted by their registry version, as Terraform trusts them: its lock file records no module hashes. The provider is pinned to its newest release that the module versions accept, counting only the modules whose adapters have a resource to map in the import; when one of them holds it back, the report says which. A module version never holds the provider back a major release: one that accepts no release of the provider's newest major isn't called, its resources stay in the root as plain resources of the newest provider, and the report names it. A nightly job opens an issue when a newer release comes out, saying whether the adapter fits it (its variables, outputs, defaults and `Inverse`, and the resources the adapter maps onto, such as `azurerm_user_assigned_identity.this`), which of the variables it sets changed type, and whether the release accepts the newest major release of each provider the adapter uses; a pinned release that is the newest but accepts only an older major release is noted in the run's summary, without an issue; `go run ./internal/adapters/cmd/adaptercheck -write`, or the `adapters` workflow run with `write` on a branch, refreshes the interfaces after a bump.

`--modules=local` uses generated local modules only, for example where the module registry can't be reached; `--modules=none` keeps every resource in the root.

## Your own modules

Modules of your own come before the curated ones. List them in the configuration file, each pinned:

```yaml
modules:
  - source: git::https://github.com/acme/terraform-modules.git//bucket?ref=v1.4.0
  - source: app.terraform.io/acme/queue/aws   # a private registry
    version: 2.1.0
  - source: ./modules/role                    # relative to the configuration file
```

A git module pins a `?ref=`: a release tag such as `v1.4.0`, or a full commit SHA, the one ref that can't move. Another ref, such as a branch, works but gets a warning, as the module it calls can change after infraharvest tested it.

infraharvest fetches each module with Terraform, so git and private registry credentials work as they do for Terraform. A module that can't change, a registry module at its version or a git module at a commit SHA, is fetched once and kept in the infraharvest cache directory (`infraharvest/modules` under the user cache directory, such as `~/.cache` on Linux); delete it to fetch again. A module at a tag or a branch is fetched on every run. A registry module whose source ends with another provider infraharvest imports, such as `app.terraform.io/acme/network/google` in an AWS import, isn't fetched at all. infraharvest matches each module by its signature: its resources, one of each type, form the cluster, around the one the others refer to. Where the module sets an argument to `var.<name>`, the call passes the imported value. Where it refers to another of its resources, the imported resource must refer to the matching one. Any other expression is the module's own, and the plan check judges it. A cluster with a setting the module doesn't take is declined, as with the curated modules. A module with `count`, `for_each`, `dynamic` blocks, nested modules or two resources of a type isn't matched yet: the log says so, and the curated modules and generated local modules apply.

## Generated local modules

Other resources that come in clusters, such as a security group and its rules, move into a generated local module when two or more clusters in a root have the same shape. The module goes in `<out>/modules/<kind>_<hash>/` (`main.tf`, `variables.tf`, `outputs.tf`, `README.md`), and each cluster becomes a call to it. Values the clusters share stay in the module, and values that differ become typed variables. References from other resources use the module's outputs, and the import blocks import into the module. Identical modules in different roots are written once. The change is kept only if a new plan shows no extra changes.

## Merged environments

Where the environments of a stack merge into one root (see [Merging environments](configuration.md#merging-environments)), their module calls merge as their resources do, by name. A call of the same module at the same release in each environment that has it, curated, your own or generated (with the same hash, so the same shape), becomes one call: what its arguments share stays as it is, a name becomes a named local, and what else differs a variable each environment sets, or a condition on `var.env`. A call only some environments make is counted by a `deploy_` variable, `module.<name>[0]`. A call of another module or release in one environment stays that environment's, with a `deploy_` variable of its own, so that each environment keeps calling what its own root called. The sources of generated local modules are written relative to the merged root, and the resources in each call are imported at their addresses in it, each environment only those its own call had, through `var.import_ids`. A call's `providers` argument, such as `{ aws = aws.without_default_tags }`, keeps its provider configuration in the merged root.
