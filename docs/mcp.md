# AI agents (MCP)

`infraharvest mcp` serves infraharvest to AI agents such as Claude Code, Copilot or Cursor over the [Model Context Protocol](https://modelcontextprotocol.io), on stdin and stdout. Its tools run the same binary, so they behave like the command line:

| Tool | What it does |
|---|---|
| `discover` | Lists a provider's resources into a selection file, and summarises what it includes and excludes, with the reasons for the first 50 exclusions and a count of the rest, which the selection file has |
| `import` | Generates configuration from a selection file. It asks the user to confirm first, through MCP elicitation. A client that can't ask gets the command to run instead |
| `report` | Returns an import's report, or with `kind` set to `drift` the drift report, `drift.md` (without `kind`, the drift report when the output directory has no import report): its first 256 KiB, cut after a whole line, and then how much is left out and where the full report is |
| `drift` | Checks the roots in an output directory for what changed in the cloud since they were applied, as [`infraharvest drift`](drift.md) does, and returns the totals, the first 200 changes, the roots that couldn't be checked and the exit code. It changes neither the code nor the state, but runs Terraform's init and plan on the roots, which run their providers with the server's credentials: it refuses roots that use other providers than infraharvest generates roots with (see below), and asks the user to confirm first, through MCP elicitation. A client that can't ask gets the command to run instead |
| `drift_accept` | Takes the cloud's values of the changes that `rules` or a `decisions` file accept into the roots' code. It refuses the roots `drift` refuses, and asks the user to confirm first, through MCP elicitation, before Terraform runs, with the rules or the decisions file. With `write_decisions`, it writes the run's changes into the decisions file. A client that can't ask gets the command to run instead |

Their parameters are named after the flags they set: `provider`, `services`, `selection` and `config`, and for `import` also `out`, `engine`, `incremental` and `regenerate`; `report` takes `out` and `kind` (`import` or `drift`). `config` is a [configuration file](configuration.md), passed on as `--config`: it has to be under `--root`, as the other files do, and sets what the other parameters don't, as on the command line, where a parameter wins over the file. Each tool takes only the settings that its command applies from the file and that its parameters set. `discover` and `import` take `engine` and `services`, and for aws `accounts`, `cfn-ignore`, `cfn-stack`, `profile` and `regions`, for azure `azapi`, `management-group`, `resource-group` and `subscriptions`, for google `folders`, `organization`, `projects` and `regions`, each under `settings` or that provider's section, with `backend` and `environments`. `drift` and `drift_accept` take `engine` and `engine-timeout` under `settings` alone, as drift applies nothing else of the file. A file that sets anything else is refused before anything runs, `drift`'s check too: `terraform-path`, which names a binary to run, settings that name files or directories, such as `catalogue` (`drift` takes it as a parameter, checked under `--root`), `managed-state` or `selection`, `modules`, the modes `incremental`, `regenerate` and `force-unlock`, which only the tools' parameters set, as the confirmation describes the run from them, a setting of one provider's for another, and every other flag the tools don't set; run the command line for those. Each tool opens the file once, refuses it if it isn't the file its path leads to under `--root` once open or if it has another name, a hard link, and runs from a private copy of what it read; selection and decisions files are read the same way. `import` checks it with the rest before the user is asked, and the confirmation lists all of it that applies to the run, every field of its settings, of the provider's section, backend and environments, with each value quoted, and says what the import reads with the scope the file sets where the parameters don't, as the command applies it; the confirmation is for that content, as for the selection file: if the agent changes the file before the run, nothing runs. Where to list is in the provider's own terms, as its command's flags are (see [AWS](aws.md), [Azure](azure.md) and [Google Cloud](google.md)):

| Provider | Parameters | Flags they set |
|---|---|---|
| `aws` | `regions`, `profile`, `accounts`, `cfn_stacks`, `cfn_ignore` | `--regions`, `--profile`, `--accounts`, `--cfn-stack` and `--cfn-ignore`, once per value |
| `azure` | `subscriptions`, `management_group`, `resource_group`, `azapi` | `--subscriptions`, `--management-group`, `--resource-group`, `--azapi` |
| `google` | `projects`, `organization`, `folders`, `regions` | `--projects`, `--organization`, `--folders`, `--regions` |

The tools reject a parameter for another provider than the table gives it, such as `regions` for Azure or `organization` for AWS, with an error naming it. The command checks the rest as it checks its flags, and the tool returns its error: a Google scope without `projects`, `organization` or `folders`, an `engine` other than `terraform` or `tofu`, or `incremental` with `regenerate`. `import` runs those checks, as `--check` does, before the user is asked to confirm, so a run the command would refuse is never put to them. The tools themselves also reject a `provider` this infraharvest doesn't have, services and regions not named like one (letters, digits and `_*.-`), an empty value in a list, a comma in a value of a list the flag takes comma-separated, such as `environments`, and any value or path with a control character such as a newline, which could make the confirmation say something else; the confirmation quotes the paths, and the command a client that can't ask is given quotes each argument for a POSIX shell. The user confirms an import seeing what it reads in these terms: the accounts and profile, the subscriptions and resource group, or the projects, organizations and folders, with the regions and services. With `cfn_stacks`, which imports the resources of those CloudFormation stacks alone (see [Migrating a CloudFormation stack](aws.md#migrating-a-cloudformation-stack)), `services` may be left out: the stacks' resource types say which to list. Unlike the command line, where `--cfn-stack` needs neither `--all` nor a selection file, `import` still takes the `selection` file `discover` wrote with the same `cfn_stacks`, for the user to confirm what it imports.

`drift` takes `out`, `config` (a configuration file under `--root`, read and checked as for the other tools, whose `engine` and `engine-timeout` under `settings` apply where the parameters don't set them; the import's own file, with its scope, backend or environments, is refused; the confirmation lists what it sets, and covers its content), `engine`, `roots` (patterns, as `--root` takes them), `parallel`, `environments` (`all` for every one, which roots of more than one environment need without naming theirs, as for `--environment`), `catalogue` (the directory of catalogue files the import used, under `--root`), `engine_timeout` (a duration such as `30m`, as `--engine-timeout` takes it) and `force_unlock`; `drift_accept` takes those too, and `rules`, `decisions` and `write_decisions`. `rules` is one ordered list of accept and keep rules, each as a line of drift's [`--rules`](drift.md#accepting-changes) file takes it: `accept` or `keep`, then `all`, or `attribute=`, `type=`, `address=` or `root=` with a pattern, such as `accept attribute=tags.*` or `keep type=aws_security_group`; a rule alone is accepted. They are passed on as `--accept` and `--keep` in their order, so the last rule that matches a change decides, as on the command line and in the GitHub Action's `drift-accept`. This replaces the separate `accept` and `keep` lists of earlier versions, which put every keep rule after every accept rule. Both tools run drift with `--format json --detailed-exitcode`, so the exit code says whether drift is left (see [Exit codes](drift.md#exit-codes)).

Both tools ask the user before Terraform runs at all, as a run executes the roots' providers: `drift` with the roots, the environments and the configuration file it checks, and `drift_accept` with those and the rules or the decisions file that decide what is written into the code. Call `drift` first, and show the user its changes, for them to know what the rules would accept: `drift_accept` doesn't check before asking. `keep` rules or `write_decisions` alone write no code, and the confirmation says so; they still run Terraform, so the user is asked all the same. The confirmation is for the decisions file as it was when the user was asked: if the agent changes it before the run, nothing is written, and the run reads the content the user confirmed from a private copy; with `write_decisions`, the merged file is then written back over it, unless it changed while drift ran. With `write_decisions` alone, the decisions file only records the changes and keeps the decisions it has. The decisions file, read or written, has to be under `--root`, as the output directory does, though the command line takes one anywhere.

Terraform's init and plan install and run a root's providers, and the modules it calls, with the credentials the server has: a provider is a program, and the `external` data source runs any program the configuration names. Roots from a cloned repository, with an agent that a prompt in it steers, could run code of the agent's choosing. Before anything runs, and again before the confirmed run, `drift` and `drift_accept` read every `.tf`, `.tf.json`, `.tofu` and `.tofu.json` file under `out`, override files too, and refuse the roots unless:

- every provider they declare in `required_providers`, configure in a `provider` block or use through a resource, data source (a `check` block's too), ephemeral resource, `provider` argument or a module call's `providers` is one infraharvest generates roots with: each provider's own (`hashicorp/aws`, `hashicorp/azurerm`, `hashicorp/google`) and those its curated modules use (`Azure/azapi`, `hashicorp/google-beta`), of the providers this binary has; never `hashicorp/external`. A provider no `required_providers` declares is `hashicorp/<name>`, as Terraform takes it;
- every module they call is under `out`, or one of infraharvest's curated modules from the public registry (see [Modules](modules.md)): a module from git, a URL or another registry module could bring providers of its own, which can't be checked before init downloads it;
- each local module directory a call leads to passes the same check, and none is in a `.terraform` or `terraform.d` directory;
- there is no `terraform.d` directory under `out`, a filesystem mirror Terraform would install providers from;
- no symbolic link under `out` leads to a directory, which Terraform follows and the check doesn't, and every link to a file it reads leads to a file under `out`.

The error names the file and line. If you trust the roots, such as roots of your own with other providers, run `infraharvest drift` on them yourself from a terminal. The tools run drift with [`--untrusted-roots`](reference/cli.md): Terraform ignores the `.terraform` directories the roots have, with whatever providers and modules a repository put there, keeping each root's working files in a private directory of the run instead, and installs providers from their registries alone, which verify what they download against the lock file and their signatures, never from a filesystem mirror. The confirmation covers the roots as they were checked, by a digest of every configuration, var, backend settings and lock file under `out`, as the check read it: the check runs again on the call with the user's answer, and if any of those files changed in between, nothing runs; drift, given the digest, checks it once more after it has locked the output directory, before Terraform runs, and refuses roots that changed. The roots' providers still run, those the check allows: confirm only for roots you trust.

The tools run one at a time per output directory, as the command line does (see [Usage](usage.md)): an `import` call into an `out` another run is writing, such as an earlier call still planning, or a `discover` call while one writes `infraharvest-out` under `--root`, the output directory `discover` saves what it lists to, fails at once with an error naming that run, and writes nothing there. The tools never pass `--force-unlock`. A call whose run is stopped by a signal says so: `discover` then doesn't read the selection file, which may be an earlier run's.

The agent can propose a selection, but only a person can start an import. The confirmation is for the selection file as it was when the user was asked: if the agent changes the file before the import runs, nothing is imported, and the import reads the content the user confirmed from a private copy. Each confirmation runs one import, and only an answer to a request the server made counts. The confirmation relies on the MCP client asking the user and passing on their answer honestly. The files the tools read and write stay under `--root` (default: the current directory, which the server refuses when it is the root of a filesystem or the home directory, as some hosts start servers there; it logs the root it uses to stderr), a relative path such as `selection.yaml` is relative to it, and a symbolic link under it that leads elsewhere is rejected: in the paths the agent names, in the report a `report` call reads, and anywhere in the output directory an import or drift writes into (Terraform's `.terraform` directories aside). infraharvest reads the cloud and writes files; it never applies anything. Hosts other than Claude Code, such as desktop apps, may start the server outside any project: pass `--root` there. To add the server to Claude Code:

```sh
claude mcp add infraharvest -- infraharvest mcp
```
