# AI agents (MCP)

`infraharvest mcp` serves infraharvest to AI agents such as Claude Code, Copilot or Cursor over the [Model Context Protocol](https://modelcontextprotocol.io), on stdin and stdout. Its tools run the same binary, so they behave like the command line:

| Tool | What it does |
|---|---|
| `discover` | Lists a provider's resources into a selection file, and summarises what it includes and excludes, with the reasons for the first 50 exclusions and a count of the rest, which the selection file has |
| `import` | Generates configuration from a selection file. It asks the user to confirm first, through MCP elicitation. A client that can't ask gets the command to run instead |
| `report` | Returns an import's report, or with `kind` set to `drift` the drift report, `drift.md` (without `kind`, the drift report when the output directory has no import report): its first 256 KiB, cut after a whole line, and then how much is left out and where the full report is |
| `drift` | Checks the roots in an output directory for what changed in the cloud since they were applied, as [`infraharvest drift`](drift.md) does, and returns the totals, the first 200 changes, the roots that couldn't be checked and the exit code. It changes neither the code nor the state, so it asks nobody first |
| `drift_accept` | Takes the cloud's values of the changes that `rules` or a `decisions` file accept into the roots' code. It asks the user to confirm first, through MCP elicitation, with how many changes a check without them found the next apply would revert, and how many of those would be accepted and kept. With `write_decisions`, it writes the run's changes into the decisions file. A client that can't ask gets the command to run instead |

Their parameters are named after the flags they set: `provider`, `services`, `selection` and `config`, and for `import` also `out`, `engine`, `incremental` and `regenerate`; `report` takes `out` and `kind` (`import` or `drift`). `config` is a [configuration file](configuration.md), passed on as `--config`: it has to be under `--root`, as the other files do, and sets what the other parameters don't, as on the command line. The tools take only a file that sets nothing but the settings their parameters set, `accounts`, `azapi`, `cfn-ignore`, `cfn-stack`, `engine`, `engine-timeout`, `environment`, `folders`, `force-unlock`, `incremental`, `management-group`, `organization`, `parallel`, `profile`, `projects`, `regenerate`, `regions`, `resource-group`, `root`, `services` and `subscriptions`, under `settings` or a provider's section, with `backend` and `environments`. A file that sets anything else is refused before anything runs, `drift`'s check too: `terraform-path`, which names a binary to run, settings that name files or directories, such as `catalogue` (`drift` takes it as a parameter, checked under `--root`), `managed-state` or `selection`, `modules`, and every other flag the tools don't set; run the command line for those. Each tool reads the file once and runs from a private copy of what it checked. `import` checks it with the rest before the user is asked, and the confirmation lists what it sets; the confirmation is for that content, as for the selection file: if the agent changes the file before the run, nothing runs. Where to list is in the provider's own terms, as its command's flags are (see [AWS](aws.md), [Azure](azure.md) and [Google Cloud](google.md)):

| Provider | Parameters | Flags they set |
|---|---|---|
| `aws` | `regions`, `profile`, `accounts`, `cfn_stacks`, `cfn_ignore` | `--regions`, `--profile`, `--accounts`, `--cfn-stack` and `--cfn-ignore`, once per value |
| `azure` | `subscriptions`, `management_group`, `resource_group`, `azapi` | `--subscriptions`, `--management-group`, `--resource-group`, `--azapi` |
| `google` | `projects`, `organization`, `folders`, `regions` | `--projects`, `--organization`, `--folders`, `--regions` |

The tools reject a parameter for another provider than the table gives it, such as `regions` for Azure or `organization` for AWS, with an error naming it. The command checks the rest as it checks its flags, and the tool returns its error: a Google scope without `projects`, `organization` or `folders`, an `engine` other than `terraform` or `tofu`, or `incremental` with `regenerate`. `import` runs those checks, as `--check` does, before the user is asked to confirm, so a run the command would refuse is never put to them. The tools themselves also reject a `provider` this infraharvest doesn't have, services and regions not named like one (letters, digits and `_*.-`), an empty value in a list, a comma in a value of a list the flag takes comma-separated, such as `environments`, and any value or path with a control character such as a newline, which could make the confirmation say something else; the confirmation quotes the paths, and the command a client that can't ask is given quotes each argument for a POSIX shell. The user confirms an import seeing what it reads in these terms: the accounts and profile, the subscriptions and resource group, or the projects, organizations and folders, with the regions and services. With `cfn_stacks`, which imports the resources of those CloudFormation stacks alone (see [Migrating a CloudFormation stack](aws.md#migrating-a-cloudformation-stack)), `services` may be left out: the stacks' resource types say which to list. Unlike the command line, where `--cfn-stack` needs neither `--all` nor a selection file, `import` still takes the `selection` file `discover` wrote with the same `cfn_stacks`, for the user to confirm what it imports.

`drift` takes `out`, `config` (the import's configuration file, under `--root` and checked as for the other tools, whose settings drift has apply, as for `--config`; `drift_accept`'s confirmation lists what it sets, and covers its content), `engine`, `roots` (patterns, as `--root` takes them), `parallel`, `environments` (`all` for every one, which roots of more than one environment need without naming theirs, as for `--environment`), `catalogue` (the directory of catalogue files the import used, under `--root`), `engine_timeout` (a duration such as `30m`, as `--engine-timeout` takes it) and `force_unlock`; `drift_accept` takes those too, and `rules`, `decisions` and `write_decisions`. `rules` is one ordered list of accept and keep rules, each as a line of drift's [`--rules`](drift.md#accepting-changes) file takes it: `accept` or `keep`, then `all`, or `attribute=`, `type=`, `address=` or `root=` with a pattern, such as `accept attribute=tags.*` or `keep type=aws_security_group`; a rule alone is accepted. They are passed on as `--accept` and `--keep` in their order, so the last rule that matches a change decides, as on the command line and in the GitHub Action's `drift-accept`. This replaces the separate `accept` and `keep` lists of earlier versions, which put every keep rule after every accept rule. Both tools run drift with `--format json --detailed-exitcode`, so the exit code says whether drift is left (see [Exit codes](drift.md#exit-codes)).

`drift_accept` asks the user only when it could write into the code: with an `accept` rule or a `decisions` file. Before asking, it runs a check without them, which writes only the drift report, and decides that check's changes as the run would, for the user to see the counts; the run they confirm checks again, so its counts differ if the cloud changed in between. The confirmation is for the decisions file as it was when the user was asked: if the agent changes it before the run, nothing is written, and the run reads the content the user confirmed from a private copy; with `write_decisions`, the merged file is then written back over it, unless it changed while drift ran. `keep` rules or `write_decisions` alone write no code, so they run without asking: the decisions file only records the changes and keeps the decisions it has. The decisions file, read or written, has to be under `--root`, as the output directory does, though the command line takes one anywhere.

The tools run one at a time per output directory, as the command line does (see [Usage](usage.md)): an `import` call into an `out` another run is writing, such as an earlier call still planning, or a `discover` call while one writes `infraharvest-out` under `--root`, the output directory `discover` saves what it lists to, fails at once with an error naming that run, and writes nothing there. The tools never pass `--force-unlock`. A call whose run is stopped by a signal says so: `discover` then doesn't read the selection file, which may be an earlier run's.

The agent can propose a selection, but only a person can start an import. The confirmation is for the selection file as it was when the user was asked: if the agent changes the file before the import runs, nothing is imported, and the import reads the content the user confirmed from a private copy. Each confirmation runs one import, and only an answer to a request the server made counts. The confirmation relies on the MCP client asking the user and passing on their answer honestly. The files the tools read and write stay under `--root` (default: the current directory, which the server refuses when it is the root of a filesystem or the home directory, as some hosts start servers there; it logs the root it uses to stderr), a relative path such as `selection.yaml` is relative to it, and a symbolic link under it that leads elsewhere is rejected: in the paths the agent names, in the report a `report` call reads, and anywhere in the output directory an import or drift writes into (Terraform's `.terraform` directories aside). infraharvest reads the cloud and writes files; it never applies anything. Hosts other than Claude Code, such as desktop apps, may start the server outside any project: pass `--root` there. To add the server to Claude Code:

```sh
claude mcp add infraharvest -- infraharvest mcp
```
