# Usage

```text
infraharvest discover <provider> [flags]     list resources into a selection file to review
infraharvest pick --selection <file>         review a selection file in the terminal
infraharvest import <provider> [flags]       generate configuration for what a selection includes
infraharvest services <provider>             list the provider's services
infraharvest verify [output-directory]       run the verification gate on generated roots again
infraharvest drift [output-directory]        find what changed in the cloud since the roots were applied
infraharvest report [output-directory]       print an import's report again
infraharvest bootstrap --config <file>       write a root that creates the state storage
infraharvest mcp                             serve infraharvest to AI agents over MCP
infraharvest version
```

Every flag of every command is in the [command-line reference](reference/cli.md). Providers add flags of their own, such as `--profile` and `--regions` for AWS or `--projects` for Google Cloud: see [AWS](aws.md), [Azure](azure.md) and [Google Cloud](google.md).

## Choosing what to import

An import must say what it imports, so a whole account never comes under Terraform by accident:

```sh
infraharvest discover aws --services=vpc,subnet,sg,s3 --regions=eu-west-2 --selection=selection.yaml
# review selection.yaml: set include to false to leave a resource out
infraharvest import aws --services=vpc,subnet,sg,s3 --regions=eu-west-2 --selection=selection.yaml
```

`discover` lists every resource it finds into the selection file, each marked included or not. By default it leaves out resources AWS creates and manages itself, with the reason: the default VPC with its subnets, route tables and internet gateway, default security groups and network ACLs, the security groups EKS creates for clusters, service-linked roles, and the log groups Lambda creates. It also leaves out what CloudFormation stacks manage, including CDK apps, with the stack named as the reason: importing those would give them two owners. To move a stack's resources to Terraform instead, `--cfn-stack` imports exactly them (see [Migrating a CloudFormation stack](aws.md#migrating-a-cloudformation-stack)). Global services such as IAM are checked against the stacks of every enabled region. Resources whose tags or labels say another Terraform state or tool manages them are left out the same way, with the tag as the reason: a `ManagedBy`, `managed-by` or `managed_by` tag (any case) naming Terraform, OpenTofu, Pulumi, CloudFormation, the CDK or Crossplane, a `Terraform = true` tag, CloudFormation's `aws:cloudformation:stack-name` tag, or the `goog-terraform-provisioned` label the Google provider gives what Terraform creates. Discover reads tags only for some types (see below), so the import also looks at the tags in the configuration Terraform generates, and leaves out the resources they mark, such as IAM roles, with the reason in the report. `--include-owned` imports them all the same, for example to move them from a state that is lost. You can include any of them by setting `include: true` on its entry. Rules in the file (`exclude: { type: aws_cloudwatch_log_group, id: "/aws/lambda/*" }`) decide resources it doesn't list, such as ones created since, but a rule doesn't include what another Terraform state or tool manages, whether a CloudFormation stack, a tag or `--managed-state` says so: those stay excluded with their reason, and only their entry, or `--include-owned`, includes them. A rule does include what the cloud manages, such as a default VPC. Each entry records the resource's tags (labels on Google Cloud) where discover can read them, and rules can match tags too: `exclude: { tags: { env: dev } }` leaves out what is tagged `env=dev`, and `{ owner: "" }` matches resources without an `owner` tag. On AWS, discover reads tags from the Resource Groups Tagging API of each region it lists (us-east-1 for the global services). It finds tags only for resources whose ID is an ARN it lists, or whose ID or name is in the ARN of a common taggable type, so IAM roles and users have none: the API doesn't list them. A bucket's configuration resources (versioning, encryption, ...) follow the bucket.

In a terminal, `discover` then opens the picker on the file (`--pick=false` skips it); `infraharvest pick --selection selection.yaml` opens it again later. The picker shows the resources as a tree, by account and region, then type. You can include or exclude one resource, or a whole type or account at once, and search by type, ID, name, note, reason or tag. `team=web` in the search shows only resources tagged `team` with a value containing `web`, and `team=` those without a `team` tag; several terms must all match. You can also show only what is new since the last `discover`. A summary keeps count of what is selected, how many roots it makes, and how many resources may become calls of curated modules. `s` saves the file and `q` leaves it as it was. Deciding on a resource marked `new` removes the mark. `discover` records each resource's account and region in the file (`scope: aws/123456789012/eu-west-2`), and the service that listed it (`service: vpc`).

`--all` imports everything the default selection includes, without a file. The report lists what was excluded and why.

Running `discover` again updates the selection file. Entries keep their decisions and notes, but for the decisions `discover` made itself, which follow what manages each resource now: an entry it included is excluded once a Terraform state, CloudFormation or another tool manages the resource, and one it excluded takes its new reason, or once nothing manages it is decided again by the rules and defaults, marked `new: true` (see [Audit](audit.md#quick-audit-discover)). Resources that no longer exist are dropped, but only where this run listed: entries of accounts, regions, projects or services it didn't list stay as they were, and so do all the entries it didn't find when it listed with `--id`, `--tag` or `--where`, or when the listing failed in part, as for an account whose credentials expired. So `discover aws --regions eu-west-1` refreshes that region and leaves the rest of the file alone. New resources are added with `new: true`, decided by the file's rules and defaults. Review those, then remove the mark.

`discover` also saves what it listed under `<out>/.infraharvest`. `import --selection selection.yaml --reuse-inventory` imports from that saved list instead of listing the cloud again, as long as it covers the same services, region and account. On a large estate, that saves the listing time a second time. Child resources, such as an S3 bucket's configuration, are still read at import.

Resources that Terraform already manages can be left out too. `--managed-state` reads existing state, in the format Terraform 0.12 and later and OpenTofu write, and excludes every resource it finds there, with the state file as the reason. State from Terraform 0.11 or earlier (format version 3) is refused: upgrade it with Terraform 0.12 or later first. The flag accepts state files, directories of them, `s3://bucket/prefix?region=...`, `gs://bucket/prefix`, or `https://<account>.blob.core.windows.net/<container>/prefix` (`blob.core.usgovcloudapi.net` and `blob.core.chinacloudapi.cn` in Azure's US Government and China clouds; any other https host is refused, so the Azure credentials go nowhere else), reading every `.tfstate` object under the prefix with the cloud's default credentials (in Blob Storage also the `<key>env:<workspace>` blobs where the azurerm backend keeps the state of workspaces other than `default`, and in S3 the `env:/<workspace>/<key>` objects where the S3 backend keeps them, at the bucket's root, for the keys under the prefix: `&workspace_key_prefix=...` names another prefix than `env:`). Resource IDs match the way Terraform reads them: Azure IDs whatever their case, and a type by its other names, such as `aws_alb` for `aws_lb` or `azurerm_virtual_machine` for `azurerm_linux_virtual_machine`. S3 state is read with `--profile`, unless the source names another with `&profile=...`. Blob Storage is read as the azurerm backend reads it: with `ARM_ACCESS_KEY`, `ARM_SAS_TOKEN` or a service principal's `ARM_CLIENT_*` variables, and otherwise Azure's default credentials, such as the Azure CLI login, which need a data role such as Storage Blob Data Reader. `tfc://<organization>/<workspace>` reads the current state of an HCP Terraform workspace, and `tfc://<organization>/<prefix>*` of every workspace whose name starts with the prefix (`?host=` names a Terraform Enterprise host), with the token `terraform login` saved or `TF_TOKEN_<host>`. `--managed-state=backend` reads the S3, GCS or azurerm backend from the configuration file (azurerm in the cloud `ARM_ENVIRONMENT` names, as the backend does), so an import run again only picks up what is new. The report then shows how much of what was discovered Terraform manages, how much another tool such as CloudFormation manages, and how much neither does. It breaks this down by type, and by account and region when the import covers more than one (`scopes` in `coverage.json`). State can hold secrets: infraharvest reads it only when asked, keeps only resource types, IDs and addresses, and needs read access to the state for it. A source that names no bucket, container, organization or workspace, or a local path that isn't there, fails the command before anything is listed, as does a `--selection` file or `--catalogue` directory that doesn't load. So does a source that holds no state once read: a directory without `.tfstate` files, a prefix without `.tfstate` objects, or a workspace pattern that matches no workspace.

When part of an estate is already under Terraform, whether written by hand or imported earlier with another tool, point `--managed-state` at that state before importing the rest. What it manages is then left out, so nothing is imported twice, and the new roots hold only what no state has yet:

```sh
infraharvest import aws --services=vpc,subnet,sg,s3 --regions=eu-west-2 --selection=selection.yaml \
  --managed-state=./existing-roots
```

A run that fails part way, such as on one region, can be run again with `--resume`: roots generated from the same resources and options since then are kept as they are, with their results, also once applied, with `imports.tf` and `moves.tf` deleted, and the roots it didn't finish are generated again from scratch. Checkpoints go into `<out>/.infraharvest`, which `.gitignore` excludes. A root an earlier import finished may be in use, so an import into it is refused, with `--resume` too and once its `imports.tf` is deleted, naming `--regenerate` and `--incremental`; only a root of which no `.tf` file is left is generated again without them. A root directory that already holds `.tf` files no checkpoint says an import wrote, such as an unrelated root, is refused rather than overwritten, and `--resume` and `--regenerate` only remove files from roots a checkpoint says an import wrote.

`--regenerate` generates the roots earlier imports generated in `--out` again, from scratch, such as after an upgrade or with other options; with `--resume` too, those generated from the same resources and options are kept. Each resource is matched by its type and import ID with where the root had it: as the root's checkpoint records it, or, for a root an older release generated, as its import blocks say, or once they are deleted, as its checkpoint says it imported. That last is a guess: for a resource moved into a module call, only the call is known, and such a resource is never handed over to another root. With `--managed-state` naming the root's own state, its local `terraform.tfstate` or where the configured backend keeps it (`--managed-state=backend`), the state says where the root has each resource instead, and what that state has stays in the root rather than being left out as managed, also what the checkpoint doesn't say the root has. What a root an earlier import generated has is never left out because another state has it too: it stays in its root, and the log says which state has it. A root whose checkpoint can't be read then fails the command, as what it has can't be told. What the state of roots infraharvest didn't generate has is left out, as without `--regenerate`. A resource keeps its label while its name still gives it, so that resources added or removed don't move the others. A root environments share is generated again from its environments' roots, and merged again (see [Merging environments](configuration.md#merging-environments)). One that gets another address all the same, such as a resource renamed in the cloud, or moved into or out of the call of a generated local module or a curated one, gets a `moved` block in the root's `moves.tf`, from where the root had it: its next plan says it "has moved to" the new address, and destroys nothing. A `moves.tf` still there from before is kept, and the new blocks follow on from it. A resource the run now puts in another root it generates too, such as with `--env-tags`, a changed environment tag or a changed `--layout`, or with `environments:` in the configuration file, which lays out the resources of a root an earlier import generated without them by environment, is handed over: the root it leaves gets a `removed` block for it in `moves.tf`, with `destroy = false`, and the root it goes to imports it. When only some instances of a resource, or only part of a module call, go, as a removed block takes no instance keys and only a whole module call, a `moved` block first moves each resource that goes to a resource of the root alone, named `departed_` and what its address was, such as `aws_subnet.departed_vpc_a_0` for `module.vpc.aws_subnet.a[0]`, and the removed block takes that. Apply the root it leaves first, then the one it goes to (see [Applying the roots](output.md#roots-between-which-resources-move)). The `removed` blocks, with `lifecycle`, need Terraform 1.7 or OpenTofu 1.10, so the root it leaves requires 1.10 or later in `versions.tf` while `moves.tf` has them; the other roots keep the release their configuration needs. A resource of another name of its type now, such as an `aws_alb` that is an `aws_lb`, or an `azurerm_virtual_machine` that is an `azurerm_linux_virtual_machine`, keeps its import ID, but no moved block can follow it, as the providers don't move state from one type to another: the root's `moves.tf` gets a `removed` block for it where the root had it, with `destroy = false`, and the root imports it again where it is now, so its next plan forgets it as the one type and imports it as the other, destroying nothing. For only some instances of a resource, or for a resource in a module call, the removed block takes a resource of the root alone, named `departed_` and what the address was, that a `moved` block moves it to first. Going to another root as the other name of its type, it is handed over as any other resource. A root left with no resources keeps only `versions.tf`, `providers.tf`, `moves.tf` and its README. So does, in its way, a root environments share whose every resource, in every environment, the run puts in other roots: see [Merging environments](configuration.md#merging-environments). A resource that goes to a root the run doesn't generate stays where it is, and is left out of the other, as `already in another root of the output`. A root is still left as it was and reported as failed, naming them, for what moved and removed blocks can't follow: a resource moved into or out of a call that a module from the registry makes itself, as moved blocks stay within a module package, and one of another name of its type in such a call; one of another type now that infraharvest doesn't know as another name of its own, which a plan would replace; only part of a call that a module from the registry makes going to another root, as a removed block takes only the whole module call, and no moved block reaches into it; one generating the root leaves out, such as one Terraform rejects; and moved blocks that would conflict, such as a `moves.tf` that moves a resource in a cycle, or that moves one that now goes to another root: apply the root and delete `moves.tf` first. What such a root would hand over is left out of the roots it would go to. Applied on the root's state, its next plan would destroy them. A resource the run no longer imports at all, such as one deleted in the cloud since, isn't counted: so that a resource the selection now leaves out stays in the state, leave its root out of the run, or remove it from the state first (`terraform state rm`). A root that fails to generate again, such as when its plan fails, is left as it was too, with the files it had, and reported as failed. The state of a root applied without a backend, its `terraform.tfstate`, stays as it is, also when the root is left as it was: generating the root never reads or writes it, and plans with an empty state instead, as with a backend, whose state an import never reaches. So the root gets import blocks for all its resources again, and its next plan on its state skips those of the resources the state has, moves the resources at other addresses, and changes nothing. `--regenerate` doesn't go with `--incremental`.

One run writes to an output directory at a time. `discover`, `import`, `verify` and `drift` hold a lock on `<out>/.infraharvest/lock` while they run, which records the holder's process ID, host and start time. A second run into the same `--out`, from another terminal or an MCP tool call, fails at once, before it lists anything, naming the run that holds it. The lock is the operating system's own, so a run that is killed releases it with its process, and the next run takes it over. `--force-unlock` writes there anyway, for a run that is stuck, or a file system that can't lock: only pass it when nothing else is writing there. A run also refuses an output directory whose `<out>/.infraharvest` is, or holds, a symbolic link, or anything else that isn't a directory or a regular file, naming it, with `--force-unlock` too: a repository it runs on, as `drift` or `import --incremental` do on a clone, could commit one there to have the run overwrite or delete a file elsewhere, such as `~/.ssh/authorized_keys`. Elsewhere under `--out`, where the roots, modules, report and `.gitignore` go, it refuses a symbolic link to a directory, one to a file outside `--out`, or one that leads nowhere, as `bootstrap` does: a run would write through such a link, or read a file of the user's through it and write it back into a root, for a commit of the output to carry. A link to a file under `--out`, such as roots sharing a file, is allowed, as is `--out` itself being a link, and the links `terraform init` makes inside `.terraform` directories.

Once the roots are in use, `--incremental` adds what is new to them instead, without changing what they have, their state neither, as in the `terraform.tfstate` of a root applied without a backend. Each new resource goes after the blocks of the file of its type, such as `network.tf` for a subnet, which keeps the blocks it has as they are, or into a new file of that name; one that has no such file goes into a file of its own, `generated_2.tf`, then `generated_3.tf` and so on. Its import blocks, variables, locals and data sources are added after the root's own, and nothing new takes a name the root uses. New resources refer to the resources the root has, such as `vpc_id = aws_vpc.main.id`. They don't repeat the tags the root's provider already applies, and those without one of them use the provider's second configuration, without `default_tags`, which the root gets if it has none. A root's resources are found from its import blocks and from the checkpoint of the import that generated it; for roots applied since, with their import blocks deleted, add `--managed-state` too. A resource another root of the output imports, by its checkpoint, is left out too, as `already in another root of the output`, with that root's path: each resource goes into one root only, so a root an earlier import generated keeps what it has even where an import now puts it in another root, such as a Google Cloud subnetwork in its region's root, which imports now put in the global root with its network. `--regenerate` hands them over with removed blocks only when it generates both roots. A root whose import didn't finish, with no checkpoint of a result or, without a checkpoint, a `generated.tf` but no README, isn't added to: it is reported as failed, and `--resume` generates it again first. The new resources are generated and planned in a directory of their own first, because planning the root itself would need its state. In the root, the other checks run on the files as merged. Clusters of new resources can become curated module calls, but they aren't moved into generated local modules.

A rule for roots in use: running a newer infraharvest never upgrades them. `--incremental` generates what it adds with the provider releases the root's own lock file, `.terraform.lock.hcl`, pins, whatever release the new infraharvest would pick for a new root, and keeps the lock file as it is; `infraharvest verify` and `infraharvest drift` plan the root with its lock file too, and read the catalogue's entries for the provider release it pins. To move a root to a newer provider, upgrade it yourself (`terraform init -upgrade`, then plan), or generate it again with `--regenerate`, whose `moved` blocks follow resources to new addresses.

A resource a root has that has been deleted in the cloud since, so that the root's next plan would create it again, is reported as no longer in the cloud, by its address and import ID: in the report (`not_in_cloud` in `coverage.json`), in the README of the root when the run adds to it, and in the log, with how many per root. A plan of the root also fails while `imports.tf` still has its import block, as there is nothing left to import. Delete that block, if it is still there, then either delete the resource's block, and anything that refers to it, and plan; or, if the resource should exist, plan to create it again. The import changes nothing the root has, and doesn't write a `removed` block, which would only take out of the state what the cloud no longer has. It doesn't change the exit code either. As when `discover` drops the entries of its selection file, a resource counts as gone only where this run listed everything of its type: in the root's account and region, with the service that lists the type, without `--id`, `--tag` or `--where`, `--reuse-inventory` or `--resource-explorer`, and with no listing that failed in part (tags that couldn't be read aside), in roots laid out with `{account}` and `{region}`, as by default. In a root environments share (see [Merging environments](configuration.md#merging-environments)), each is reported at its address in the merged root, as the environment's (`environment` in `coverage.json`); with nothing new, the merged root stays as it is, as a plan of it would fail to import what is gone. Where the run adds something new to the merged root, the merge keeps what is gone as it was, its block, its import block and the environment's import ID, and plans each environment without importing what it no longer has, which the plan may create again; what the merged root has keeps its addresses. A resource the selection now leaves out isn't gone: the listing still finds it. Nor are the types it leaves out whole, by the selection file's defaults or a rule on the type alone, looked at: an import skips the calls that would list only those. Types a listing can't tell about aren't looked at: types the catalogue doesn't know; children such as a bucket's configuration, which follow their parent; Azure types that Resource Graph maps one by one through Resource Manager; and types a listing finds only in part, such as Google Cloud subnetworks in a region's import, which the import of global lists, or an Aurora global cluster, listed in its primary cluster's region only, or an Azure custom role, listed only while every scope it can be assigned at is in the run. The roots looked at are those the run adds to, the ones it lists a resource for, and only their resource blocks, not what their module calls hold. Finding what is gone takes no cloud call of its own: it compares the root with what the run listed.

```sh
infraharvest discover aws --regions=eu-west-2 --selection=selection.yaml   # marks what is new
infraharvest import aws --regions=eu-west-2 --selection=selection.yaml --incremental --managed-state=backend
```

## Services

A provider lists its resources service by service, and `--services` (`-s`) says which services: `--services=vpc,subnet,sg,s3`. Every `import` and `discover` needs it, on the command line or in the [configuration file](configuration.md). `--services='*'` stands for all of the provider's services except the opt-in ones (quote the `*` so the shell leaves it alone). `--skip` then leaves services out, whether they were named one by one or through `*`:

```sh
infraharvest discover aws --services='*' --skip=iam,organization --regions=eu-west-2
```

`infraharvest services <provider>` prints a provider's services, and the [services reference](reference/services.md) gives the Terraform types each one lists. A service name the provider doesn't have fails like a service that can't be listed. Azure's opt-in services are listed only when `--services` names them: those that list what `resource_graph` lists already, each one kind of resource through Resource Manager, such as `virtual_network`, and `diagnostic_setting`, which takes a request for each resource it lists the diagnostic settings of (see [Azure](azure.md#diagnostic-settings)). A service such as `diagnostic_setting` that lists from what the other services listed lists once they are done. AWS's opt-in services are those of services at end of support, WAF Classic and MediaStore (see [AWS](aws.md#services-at-end-of-life)).

Services are listed several at a time (`--list-parallel`, 4 by default). One that fails, or takes longer than `--list-timeout` (30 minutes by default), is left out of the output and reported, and the run exits with 1, or with 3 under `--allow-partial` (see [Exit codes](output.md#exit-codes)). One that listed but failed on a part, such as `route53` when the records of a hosted zone fail to list, keeps what it listed, and is reported and sets the exit code the same way. So do tags that fail to read, as when `tag:GetResources` is denied: selection rules by tag, owner detection, `{env}` layouts and the report's counts by tag would miss them, so the run goes on with what it has but doesn't pass as complete.

## Listing through Terraform

Every provider has an opt-in `query` service that lists resource types no other service lists through Terraform's own list resources (`terraform query`, Terraform 1.14 or later). `--query-types` names the types, and `--services` must name `query`:

```sh
infraharvest discover aws --services=query --query-types=aws_flow_log,aws_dsql_cluster --regions=eu-west-2
```

The types must be the provider's, and have a list resource in the provider release the generated roots pin (`terraform providers schema -json` lists them under `list_resource_schemas`). A type another service lists, as the [services reference](reference/services.md) has it, is refused, with the service to name instead: that service reads what the generated configuration needs, such as tags. Where another service of the same run lists a type after all, as Azure's `resource_graph` can list any type Resource Graph returns, the `query` service's resources of that type are left out, and the log says so. A type whose list resource needs arguments infraharvest has no value for, such as `aws_api_gateway_resource`'s `rest_api_id`, is refused too, and so is the `query` service with `--engine=tofu`, as OpenTofu has no `terraform query`.

The `query` service lists in the same account and region, subscription or project as the other services, with the credentials Terraform is given for the import, and keeps only what belongs there: on AWS, the global import takes the resources whose identity has no region; on Google Cloud, a region's import takes those in the region or its zones, and the global one the others; on Azure, `--resource-group` keeps that group's. Terraform runs in a private directory under `<out>/.infraharvest`, removed when the listing is done, with the provider release the generated roots pin, so that the roots import with the release that listed: the newest, unless a curated module that what the other services listed may be called in holds it back (see [Modules](modules.md)). The `query` service lists once the other services are done, for that.

Terraform is asked for identities only, not the resources' attributes, and the import brings each resource in by its identity (`import { identity = { ... } }`), which needs Terraform 1.12: the plan reads each resource anyway. The run then uses Terraform 1.14 or later throughout, from `PATH`, `--terraform-path` or a download. A resource listed this way has its identity's attributes as its ID in the selection file, such as `account_id=123456789012,name=/app/logs,region=eu-west-2`, and `--id` takes it whole and `--where` filters on its attributes (see [Filtering](#filtering)); it has no tags, as Terraform's list resources return none, and infraharvest reads none for it, which would take a call per resource. So `--tag` leaves it in. A selection file's rule on tags that matches it otherwise can't be told to match: it excludes it, with the reason `excluded by a rule in the selection file on tags, which Terraform's list resources don't return`, until its entry includes it or a later rule without tags decides it. Environment tags, `--env-tags` or the configuration file's environments split by tags, can't place it: it goes where resources without them do, and the report warns of it. What its tags say manages it, such as a `ManagedBy` tag, the import finds in the configuration Terraform generates, as for IAM roles (see [Choosing what to import](#choosing-what-to-import)); `discover` doesn't see it. `--managed-state` leaves it out when a state, written by Terraform 1.12 or later, has its identity.

Each list returns at most 10,000 resources. A list that reaches the limit, or fails, such as one Terraform is refused, is reported for its type, and the run doesn't pass as complete, as with a service that listed in part; the other types' resources are kept.

## Running in parallel

Two flags set how much of an import runs at once:

| Flag | Default | What runs at once |
|---|---|---|
| `--list-parallel` | `4` | the services listed for one account and region, subscription or project |
| `--parallel` | `1` | the accounts, subscriptions or projects, and their regions, imported together; the limit counts all of them, so `--parallel 4` never runs more than four at once |

`--parallel` stays at 1 by default because each account, subscription, project or region it runs at once has a Terraform of its own, with its provider loaded, so memory use grows with it. Listing is quick next to generating: in an AWS region, listing takes seconds and generating its roots takes minutes. So the time `--parallel` saves is close to the generate time of every region or account beyond the first, which makes it worth raising for an import of many regions or accounts:

```sh
infraharvest import aws --services='*' --regions=eu-west-1,eu-west-2,us-east-1 --all --parallel 3
```

Start at 2 to 4 and watch the machine's memory, more on a large machine. The global services and those only in us-east-1 (AWS) and a project's first region (Google) are still imported first, on their own, as the other regions refer to them. The output is the same whichever `--parallel` is set, and the report keeps the order of `--regions`.

Lower `--list-parallel` when an API throttles the listing, as the requests of every service listed at once count towards the same limits.

## Filtering

`--id`, `--tag` and `--where` keep only some of what the services list. Each can be given several times, and the selection file and the picker still decide among what passes. Values are separated by commas.

**IDs.** `--id <type>=<id>[,<id>...]` keeps only the resources of that type with one of those IDs, as the lister recorded them: a VPC's ID on AWS, a bucket's name, a full resource ID on Azure. The type is the Terraform type without the provider's prefix: `vpc` for `aws_vpc`, `virtual_network` for `azurerm_virtual_network`, `storage_bucket` for `google_storage_bucket`.

```sh
infraharvest import aws --services=vpc,subnet --regions=eu-west-2 --all --id=vpc=vpc-0a1b2c3d,vpc-4e5f6a7b
infraharvest import google --services=cloud_asset --projects=my-project --all --id=storage_bucket=my-logs
infraharvest import azure --services=virtual_network --all \
  --id=virtual_network=/subscriptions/<subscription>/resourceGroups/web/providers/Microsoft.Network/virtualNetworks/web
```

An `--id` applies to its own type only: the first example keeps every subnet, and an S3 bucket's policy (`aws_s3_bucket_policy`) is a type of its own, which `--id=s3_bucket=my-logs` doesn't narrow. Give an `--id` for each type to narrow, as in `--id=s3_bucket=my-logs --id=s3_bucket_policy=my-logs`. Several `--id` on one type must all match, so to keep several IDs of one type, list them in one `--id`. The ID of a resource the `query` service lists is its identity, `<key>=<value>` pairs separated by commas (see [Listing through Terraform](#listing-through-terraform)): an `--id` whose every value is such a pair takes them whole, as one ID, such as `--id=flow_log=id=fl-0a1b2c3d,region=eu-west-2`. To keep several of one type, filter on an attribute of their identities with `--where` instead, such as `--where=name=/app/logs,/app/audit`, which applies to every type the run lists.

**Tags.** To choose resources by tag on every service, use the selection file's rules. Rules decide each resource discover adds to the file, so write them before the first `discover`, into the file it will write:

```yaml
version: 1
defaults:
  include: false
rules:
  - include: { tags: { Environment: prod } }
  - exclude: { type: aws_cloudwatch_log_group, tags: { owner: "" } }
  - exclude: { type: "aws_s3_bucket*", name: "*-scratch" }
```

A rule matches by `type`, `id`, `name` and `tags`, each a pattern or a list of patterns, in which `*` matches any text; a resource matches when every field the rule gives has a pattern it matches. `name` is the resource's name as the lister records it, the `name` of its entry in the selection file: a queue's, bucket's or topic's name, not its URL or ARN. A bucket's configuration resources (`aws_s3_bucket_versioning` and the rest) have the bucket's name, so the last rule leaves out the buckets whose names end in `-scratch` with their configuration. The last rule that matches a resource decides it, else the defaults: here everything tagged `Environment=prod` is included, but for its log groups without an `owner` tag, its `-scratch` buckets, and what another Terraform state or tool manages, such as a CloudFormation stack's resources: a rule doesn't include those (see [Choosing what to import](#choosing-what-to-import)). In a file discover already wrote, each listed resource keeps its decision, and rules decide only the resources it doesn't list yet, such as ones created since. To change those decisions, set `include` on the entries, or find them by tag in the picker. Rules match the tags discover reads, so resources it reads no tags for, such as IAM roles and users on AWS, match only `""` (see [Choosing what to import](#choosing-what-to-import)).

**Filtering while listing.** `--tag <key>=<value>[,<value>...]` keeps the resources whose tag has one of the values, and `--tag <key>` those that have the tag at all. `--where <path>=<value>[,<value>...]` does the same for the attribute at a dotted path, as the lister records it, such as `tags.Environment` (what `--tag Environment` filters on). They apply to every type, and save the requests of what they leave out, but only the listers that support them apply them, as they list; the others ignore them, so the import logs a warning for each. Only these AWS listers support them, on tags:

| Service | Example |
|---|---|
| `ec2_instance` | `--tag Environment=prod` |
| `ebs` | `--tag team=web,data` |
| `api_gateway` | `--tag owner=payments` |

A REST API left out by a filter takes its stages, resources, methods and the rest with it. On every other service, filter by tag with the selection file's rules, as above.

## Day to day

Once the roots are applied (see [Applying the roots](output.md#applying-the-roots)), an import is something you run again:

| To | Use |
|---|---|
| Add new resources to the roots | `discover` again, review what it marks `new`, then `import` with `--selection` and `--incremental`; once a root's `imports.tf` is deleted, add `--managed-state` (see [Choosing what to import](#choosing-what-to-import)) |
| Find what the roots have that was deleted in the cloud | `import` with `--incremental`: the report, and the README of each root it adds to, list it as no longer in the cloud, with what to do (see [Choosing what to import](#choosing-what-to-import)) |
| Finish a run that failed part way | The same command with `--resume`: roots generated from the same resources and options are kept, those it didn't finish generated again |
| Generate the roots again, such as after an upgrade | `import` with `--regenerate`: resources at other addresses get moved blocks, those that go to another root it generates get removed blocks, and a root whose resources go where neither can follow them is left as it was (see [Choosing what to import](#choosing-what-to-import)) |
| Import what `discover` just listed, without listing again | `--reuse-inventory`, with the same `--out`, services and filters |
| Check roots after editing them | `infraharvest verify [output-directory]`, before deleting `imports.tf` (see [Verification gate](output.md#verification-gate)) |
| Check the roots against your own rules | `--policy <dir>` on `import` or `verify`, with conftest installed: your OPA policies run in G5, and what they find is listed, without failing the check (see [Your own policies](output.md#your-own-policies)) |
| See what changed in the cloud since applying | `infraharvest drift [output-directory]`: one refresh per root, with read access to the state; it reports which changes the next apply would revert, and changes nothing (see [Drift](drift.md)) |
| Keep what changed in the cloud | `infraharvest drift [output-directory] --accept <rule>`, such as `--accept 'attribute=tags.*'`: the cloud's values of the changes the rules accept are written into the code, once a plan of the edited code shows them taken (see [Accepting changes](drift.md#accepting-changes)) |
| Review changes in the cloud one by one | `infraharvest drift [output-directory] --write-decisions` writes `drift.yaml`, a decisions file with an entry per change; set each to `accept` or `keep`, then run `infraharvest drift [output-directory] --decisions <out>/drift.yaml` (see [Decisions file](drift.md#decisions-file)) |
| See what in an account isn't managed by Terraform, without importing | `discover` with `--managed-state`, then read the selection file; for counts by type, account and tag, `import --all` into a scratch `--out` (see [Audit](audit.md)) |
| Print the report again | `infraharvest report [output-directory]`, with `--format json` for JSON |
| Use the result in a script | `--format json` prints the report on stdout, and logs go to stderr; the exit code says whether the import is complete (see [Exit codes](output.md#exit-codes)) |
| Keep what imported when something fails | `--allow-partial`: what failed is left out and reported, and the run exits 3 instead of 1 |
| Import faster | `--parallel` for accounts, subscriptions, projects and regions, `--list-parallel` for services (see [Running in parallel](#running-in-parallel)) |
| Split roots by environment | `--env-tags=Environment`, or `{env}` in `--layout`; `--default-env=dev` puts what no tag places in `dev` instead of `shared` (see [Layout](output.md#layout)) |
| Share one root between environments | `environments:` in the [configuration file](configuration.md#environments): each stack's roots of its environments merge into one root, with each environment's values in `vars/<env>/`; `--merge-environments=false` keeps a root per environment (see [Merging environments](configuration.md#merging-environments)) |
| Check a root environments share | `infraharvest verify [output-directory]` plans it once per environment, with its var files; `--environment=prod` plans one, with that environment's credentials. `infraharvest drift --environment=prod` checks it for drift likewise |
| Choose what becomes a module call | `--modules`: `registry` (the default), `latest-untested`, `local` or `none`; your own modules go in the [configuration file](configuration.md) (see [Modules](modules.md)) |
| Import less | `--services` and `--skip`, then `--id`, `--tag` and `--where` (see [Filtering](#filtering)) |
| Run on a schedule | The [GitHub Action](https://github.com/IgnatG/infraharvest/blob/main/action/README.md), which can open a pull request with the result |
| Check drift on a schedule | The [GitHub Action](https://github.com/IgnatG/infraharvest/blob/main/action/README.md#drift) with `drift: report` or `drift: accept`: it adds `drift.md` to the job summary, sets `drift-found`, and can open a pull request with the accepted edits, alone (`import: "false"`) or with an import |
| Let an AI agent prepare a selection | `infraharvest mcp` (see [AI agents](mcp.md)) |

## Options that go together

| Options | Rule |
|---|---|
| `--selection`, `--all` | `import` needs exactly one of them |
| `discover` with `--all` | Refused: `discover` lists everything, and its `--selection` names the file it writes (default `selection.yaml`) |
| `--services`, `--skip` | `--services` is required, on the command line or in the configuration file; `--skip` leaves services out of it. Both must name services the provider has, or `*` |
| `--query-types`, the `query` service | One needs the other; not with `--engine=tofu` (see [Listing through Terraform](#listing-through-terraform)) |
| `--incremental` with `--resume` | A root whose import didn't finish is generated again, then added to; with `--incremental` alone, such a root is reported as failed |
| `--regenerate`, `--incremental` | One or the other: `--regenerate` generates the roots again, `--incremental` only adds to them |
| `--regenerate` with `--resume` | The roots generated from the same resources and options are kept, the others generated again |
| `--incremental` with `--managed-state` | A root's import blocks, or the checkpoint in `<out>/.infraharvest` of the import that generated it, say what it has; with neither, `--managed-state` is required. The states of the environments of a root environments share, from their `vars/<env>/backend.hcl` or workspaces, are that root's own: what they have isn't left out as managed elsewhere, with `--resume` and `--regenerate` too |
| `--incremental` with `--reuse-inventory`, `--id`, `--tag`, `--where` or `--resource-explorer` | What the roots have that the listing doesn't find isn't reported as no longer in the cloud: such a listing can leave out what is still there |
| `--managed-state=backend` | Needs a configuration file with an `s3`, `gcs` or `azurerm` backend |
| `--reuse-inventory` | For `import`: takes what `discover` saved into the same `--out`, if it lists the services with the same `--id`, `--tag` and `--where`, for the same account and region; otherwise it lists again |
| `--layout` | Starts with `{out}/`, and uses only `{out}`, `{provider}`, `{account}`, `{region}`, `{service}` and `{env}` |
| `--layout` with several scopes | Must contain `{account}`: on AWS with `--accounts` or `--organization`, on Azure with more than one subscription, on Google Cloud with more than one project (or `{provider}/{service}` there) |
| `--merge-environments` | Merges only with `environments:` in the configuration file; set to `true` without them, it is an error. Its roots of a stack must be one per environment, outside the merged root's directory |
| A merged stack with `--incremental` | A run with only some of the stack's environments merges the others from their kept roots, unplanned: plan each with `infraharvest verify --environment`, with its credentials. Without `<out>/.infraharvest/`, as in a fresh checkout, the merged root is told from its files, and the run must have every environment of the stack, and, once the import blocks are deleted, `--managed-state` with their states (see [Merging environments](configuration.md#merging-environments)) |
| A merged stack and a new environment | An environment the merged root doesn't have yet joins it: the stack merges again with every environment, those the run lacks from their kept roots, unplanned. Where that would give what the merged root has other addresses, the new environment keeps roots of its own, and the report says why |
| `--env-tags` with `--layout` | A layout of your own needs `{env}`; `{env}` without `--env-tags` reads `Environment`, `environment`, `Env` or `env` |
| `--default-env` | Needs `--env-tags` or `{env}` in `--layout`, and doesn't go with `environments:` in the configuration file |
| AWS `--accounts`, `--organization` | One or the other; with either, `--assume-role` must contain `{account}` |
| Azure `--subscriptions`, `--management-group` | Combine, and without either the import covers `ARM_SUBSCRIPTION_ID`; `--resource-group` narrows each subscription to that group |
| Google Cloud `--projects`, `--organization`, `--folders` | Combine; at least one is required |
| `--allow-partial` | Turns exit code 1 into 3; an import that can't run still exits 2 |

`--check` checks these rules, and the rest of what a run would check before listing (the flags the configuration file sets, the selection file, the `--managed-state` sources and the `--catalogue` directory), and exits without listing anything: 0 if the run could start, 2 with the error otherwise, such as `infraharvest import aws --services=vpc --all --check` in a pipeline before the run itself. A provider command takes flags only: an argument, such as `--check` after a `--`, is an error (`unknown command`), with exit code 2.
