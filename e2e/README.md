# End-to-end tests

These tests run infraharvest against local cloud emulators, so they need no cloud account and cost nothing. CI runs them on every pull request, except the sandbox tests, which run against a real AWS account, Azure subscription or Google Cloud project, and only by hand (see [AWS sandbox](#aws-sandbox-a-real-account), [Azure sandbox](#azure-sandbox-a-real-subscription) and [Google Cloud sandbox](#google-cloud-sandbox-a-real-project)).

A test whose emulator or sandbox isn't set up skips. CI sets `INFRAHARVEST_E2E_REQUIRED=1`, which makes it fail instead, so a broken setup doesn't pass as a run that tested nothing.

## AWS (Floci)

[`TestAWSRoundTrip`](aws_test.go) uses [Floci](https://github.com/floci-io/floci), an open-source AWS emulator:

1. Terraform creates the resources in [`testdata/aws`](testdata/aws/main.tf) in Floci.
2. `infraharvest import aws --all` imports them.
3. Terraform plans the generated configuration, with the secret variables set to the values from step 1. Every resource must be an import with no changes, no resource may be left out (`rejected.hcl`), and every resource type created in step 1 must be imported.

Two more tests import the same resources: `TestAWSSelection` imports again from the selection file `infraharvest discover aws` writes, which must give the same files as `--all` byte for byte, and `TestAWSIncremental` adds what a selection left out with `--incremental`. CI runs each on a runner of its own; run in one process, they share the resources the first one creates.

[`TestAWSSelectionRules`](selection_rules_test.go) runs with `TestAWSSelection` and imports the same resources through a selection file of rules alone, with nothing included by default: queues by a tag, and not those without it (`{ Project: "" }`), buckets and their configuration by a name glob (`name: "infraharvest-e2e-*"`), with an exclude rule after it for the logs bucket, and topics without an `owner` tag. What the rules include must be imported, and nothing of a type they don't name; the logs bucket must be left out by the rule, and its versioning not imported, the VPC by the file's defaults, and the bucket of the CloudFormation stack, which a rule can't include, as the stack's.

[`TestAWSSelectionCloudFormation`](cloudformation_stack_test.go) runs with them and imports the CloudFormation stack of the same resources with `--cfn-stack`, without `--services` or a selection file: the stack's bucket must be imported, and nothing but it and its configuration, the rest excluded as outside the scope; and, the bucket having no `DeletionPolicy`, the report must say the stack isn't safe to delete and write a copy of its template that retains the bucket.

[`TestAWSSelectionCloudFormationMCP`](cloudformation_stack_test.go) runs with them and does the same through the MCP server's tools, with `cfn_stacks` and without `services`: `discover` must include the stack's bucket and nothing else, and `import` must ask once, naming the stack and saying it lists the services of the stack's resources, import the bucket and its configuration alone, with exit code 0, and report the stack as not safe to delete.

[`TestAWSDrift`](drift_aws_test.go) checks `infraharvest drift`, on a runner of its own, with an account of its own. It imports two queues and a bucket ([`testdata/aws-drift`](testdata/aws-drift/main.tf)), which share a `Project` tag, applies the roots into local states, and changes the resources out of band by applying the fixture again with other variables. A queue's tag and retention changed, drift must report both as `kept`, exit with 4 with `--detailed-exitcode`, write `drift.json` (`schema_version` 1) and `drift.md`, and leave the code as it was. With `--accept` and `--keep`, the last rule that matches a change decides it. `--write-decisions` must write the retention's entry as `undecided`; set to `accept`, it must be kept and marked `decision_stale` once the retention changes again, and, set to `accept` again, be written. The `Project` tag changed on every resource must be one change of `local.tags`, covering both queues, and the bucket's own tag, in a call of the s3-bucket module, a change traced to the call's `tags` (`source.module_path`); accepted, both are written there. The code must then plan no change, with a refresh and, once the state is refreshed, without one, and drift must find nothing. Imported again with a root per service (`{service}` in `--layout`) and applied, once the queue's and the bucket's `team` tags change, drift with `--parallel=3` and `--format=json` must print `drift.json` exactly as it writes it, find each root's change, and, with `--accept`, write each into its own root, which must then plan no change.

[`TestAWSDriftBackend`](drift_backend_test.go) runs on the same runner, with an account of its own. It imports two queues ([`testdata/aws-drift-queues`](testdata/aws-drift-queues/main.tf)) with an S3 backend in the emulator, set in a configuration file, in the bucket the fixture creates, and applies the root, so that its state is in the bucket and not in the root. A queue's tag changed out of band, drift must initialise the root with its backend (`backend` `s3` in `drift.json`), report the change as `kept`, exiting with 4 with `--detailed-exitcode`, and leave the code as it was; with `--accept`, it must write the change into the code, which must then plan no change, and, once the state in the bucket is refreshed, drift must find nothing.

[`TestAWSDriftMCP`](drift_mcp_test.go) runs on the same runner too, with an account of its own. It imports the same fixture into a local state, applies the root and changes a queue's tag out of band, then drives the MCP server's drift tools over an in-process session, with a client that confirms what the server asks; the server runs infraharvest in the test's process. `drift` must report the change as `kept`, with exit code 4, ask nothing and leave the code as it was; `drift_accept` with an accept rule must ask once, saying it would accept the change, and then write it into the code, with exit code 0; `drift` must then find it absorbed, with exit code 0, and the code must plan no change.

[`TestAWSMCP`](mcp_test.go) drives the MCP server's other tools the same way, on a runner it shares with the two tests below. It creates two queues ([`testdata/aws-mcp`](testdata/aws-mcp/main.tf)) in each of two accounts of its own, dev's and prod's. `discover` must list dev's two queues, both included; with the jobs queue then excluded in the selection file, `import` must ask once, for one resource with one excluded, and import the orders queue alone, with exit code 0; `report` must return the import's `report.md` as it is. The two accounts are then imported at once with a configuration file naming them as the environments `dev` and `prod`, which must merge into one root, applied as each environment into its workspace; with dev's orders queue's tag changed out of band, `drift` with `environments: [dev]` and dev's credentials must check the root as dev alone and report the change as `kept`, of `dev`, with exit code 4; as prod, with prod's credentials, it must find nothing, with exit code 0; and `report` with `kind: drift` must return `drift.md`.

[`TestAWSMCPImport`](mcp_import_test.go) runs with `TestAWSMCP`, in an account of its own, and drives the `import` tool into an output again, on the queues of [`testdata/aws-drift-queues`](testdata/aws-drift-queues/main.tf): with a configuration file that sets `terraform-path`, it must be refused before the user is asked, writing nothing; with one that gives the roots an S3 backend in the fixture's bucket, it must ask once, saying the file applies and naming the bucket, and import the orders queue into a root with that backend; with the jobs queue included again and `incremental`, it must ask to add what the roots don't have, add the jobs queue alone to the root, after what it had, and report the orders queue as already in the root; and with `regenerate`, it must ask to generate the roots again and import both queues into the same root, moving nothing.

[`TestAWSDriftMCPRules`](drift_mcp_test.go) runs with them too, in an account of its own, on the same fixture, applied, with the orders queue's `team` tag and the jobs queue's `owner` tag changed out of band. `drift_accept` with the ordered `rules` `keep attribute=tags.team`, then `accept attribute=tags.*`, must ask, saying it would accept both, the last rule that matches deciding; declined, the code must stay as it was. The other way round, it must ask to accept one and keep one, and write the owner alone into the code, keeping the team. With `write_decisions` alone it must ask nothing, change no code and write `drift.yaml`, the team's change undecided. With the team accepted there, and the owner changed again, `drift_accept` with the file and `write_decisions` must ask, accept the team by its entry, keep the new owner, and copy the merged file back from the private copy it ran on: the team's entry still accepted, and the owner's new change added undecided.

Two tests create resources of their own, in accounts no other test uses, and share a runner in CI: [`TestAWSParallelAccounts`](accounts_test.go) imports two accounts at once (`--accounts`, `--parallel=2`), and [`TestAWSParallelRegions`](regions_test.go) imports the global services and two regions of an account ([`testdata/aws-regions`](testdata/aws-regions/main.tf): a role and a log group in each region) twice, with `--parallel=1` and `--parallel=2`. The log must show the two regions listing or generating at the same time only with `--parallel=2` (from `aws: importing resources in region …` to `aws: listed resources in region …`, and from `aws: generating the roots in region …` to `aws: generated the roots in region …`), both imports must write the same files, and every root must plan as imports with no changes.

[`TestAWSRegistryModuleMoves`](moves_registry_test.go) shares their runner. It plans two roots ([`testdata/aws-registry-moves`](testdata/aws-registry-moves)) with the engine, against Floci: one moves a bucket into a call of the curated s3-bucket module from the registry, the other moves one out of such a call the root still makes. Each plan must succeed: moved blocks stay within a module package, but a call the root makes is the root's own, so Terraform and OpenTofu both accept moves into and out of it.

[`TestAWSQuery`](query_aws_test.go) shares their runner too. It creates a VPC flow log ([`testdata/aws-query`](testdata/aws-query/main.tf)), a type no lister lists, in an account and region of its own, `131313131313` and `ap-southeast-2`, and takes it through the `query` service (`--services=query --query-types=aws_flow_log`), which lists through Terraform's list resources: with `--engine=tofu` the import must be refused, as OpenTofu has no `terraform query`; `discover` must list the flow log under the `query` service, included, by its identity; and the import of it alone (`--id`) must write an import block by identity, with no `id`, and the flow log's block in `flow_log.tf`, its type family's file, pass every check and plan as one import with no changes. The service always runs Terraform 1.14 or later, which the test finds or downloads with `E2E_ENGINE=tofu` too. `TestAzureQuery` and `TestGoogleQuery` do the same on the other emulators.

[`TestAWSRegenerateMoves`](moves_test.go) runs on a runner of its own, with the two tests below, each with an account of its own. It imports three queues ([`testdata/aws-moves`](testdata/aws-moves/main.tf)) into one root per environment (`--env-tags=Env`) and applies the `dev` root into a local state. It then gives one queue another `Name` tag, so another address, and another the `prod` environment, so another root, and imports again with `--regenerate`. The third queue must keep its address. `moves.tf` of the `dev` root must have a `moved` block for the first queue and a `removed` block, with `destroy = false`, for the second; the gate, G8 included, must pass; the `prod` root must import the second queue; both READMEs must name the other root; and `report.json` must list them under `moved` and `departed`. Planned over the state the first apply left, the `dev` root must show the first queue as moved and forget the second, creating and destroying nothing. Applied, then the `prod` root applied, neither root may plan any change.

[`TestAWSRegenerateLayout`](moves_layout_test.go) imports two queues and a topic ([`testdata/aws-layout`](testdata/aws-layout/main.tf)) into one root, by the default layout, and applies it into a local state. It then imports again with `--regenerate` and a root per service (`--layout={out}/{provider}/{account}/{service}/{region}/`). The old root must keep its provider configuration and a `moves.tf` with a `removed` block, with `destroy = false`, for each resource, and no `imports.tf` or `generated.tf`; the gate, G8 included, must pass; the roots of `sqs` and `sns` must import what it hands over; the READMEs must name each other; and `report.json` must list each resource under `departed`. Planned over the state the first apply left, the old root must forget every resource, creating and destroying nothing. Applied, then the new roots, each importing what it is handed with no changes, no root may plan any change, and the fixture must still find its resources as it left them.

[`TestAWSRegenerateModules`](moves_modules_test.go) imports two roles, each with a policy of its own ([`testdata/aws-module-moves`](testdata/aws-module-moves/main.tf)), with `--modules=none`, and applies the root into a local state, in a copy of the output with its generated modules at the same paths. Imported again with `--regenerate` and `--modules=local`, the roles, clusters of one shape, must become calls of a generated local module, one per role: `moves.tf` must move each resource into its call, the gate, G8 included, must pass, and `report.json` must list the moves. Planned over the state of the first apply, the root must show each resource as moved, creating and destroying nothing, and, applied, plan no change. With `moves.tf` deleted, as the README says once it is applied, and imported again with `--modules=none`, `moves.tf` must move each resource back out of its call, with the same plans.

[`TestAWSRegenerateCuratedModules`](moves_modules_test.go) does the same with two buckets, each with its versioning ([`testdata/aws-curated-moves`](testdata/aws-curated-moves/main.tf)), and `--modules=registry`: each bucket becomes a call of the curated s3-bucket module from the registry, which `moves.tf` moves its resources into, and, with `--modules=none` again, out of.

[`TestAWSEnvironments`](environments_aws_test.go) runs on a runner of its own. It creates [`testdata/aws-environments`](testdata/aws-environments/main.tf) in two accounts of their own, `777777777777` and `888888888888`, which a configuration file maps to `dev` and `prod`, and imports both at once: a queue of another size in each, an alerts topic and queue prod alone has, a queue configured too differently to merge, and three queues of one shape in each, whose retention differs between the environments. The two environments' roots must merge into `aws/us-east-1`, with the size a variable, the alerts a `deploy_alerts` feature and each environment's odd queue its residue, named from a local as the shared queues are, and planned as each environment, with that account's credentials and its var files, the merged root must import what the environment has and change nothing. `--resume` must keep the merged root as it was; `--incremental`, once dev gets another queue, must add it as dev's, every environment still planning with no changes. An `--incremental` import of dev alone, once dev gets a reports queue, must merge prod again from its kept root, unplanned, with the report saying so, and both environments must still plan with no changes. Once each environment applies the merged root into its workspace and dev's queue changes size in the cloud, `drift --environment=dev` must report the change as dev's and, accepted, write it into dev's `vars/dev/terraform.tfvars` alone, with no code written, and `drift --environment=prod` must find no drift. Then, as from a fresh checkout of the output, with `.infraharvest/` deleted, and `imports.tf` and each environment's `imports.tfvars` deleted as after the apply, prod gets a billing queue: `--incremental` with `--managed-state` on the environments' workspace states must tell the merged root from its files and add that queue into it as prod's, and nothing else; planned in its workspace, dev must change nothing and prod import the queue alone. A `--layout` that puts the environments' roots in the merged root's directory must keep them apart, the report saying why.

[`TestAWSEnvironmentsDrift`](environments_aws_test.go) and [`TestAWSEnvironmentsRegenerate`](environments_aws_test.go) each run on a runner of their own, with the fixture applied as `TestAWSEnvironments` leaves it. In `TestAWSEnvironmentsDrift` ([`environments_drift_test.go`](environments_drift_test.go)), the accounts are imported with an S3 backend, each account holding a state bucket of its own: the channel queues must be one resource with `for_each` over a map variable each environment's var file sets. Each environment initialises the merged root with its `vars/<env>/backend.hcl`, prod's pointed at prod's bucket, and applies it. Once dev's email queue changes retention and prod's alerts queue, of the `deploy_alerts` feature, its delay, drift as each environment, with its credentials, must read the state from its bucket (`backend` `s3`) and report its change as `kept`, its address the `for_each` key or the feature's `[0]`, and `--write-decisions` must write an entry for each with its `environment`. Accepted in the decisions file, dev's change must be written into the email key of dev's map variable alone, and prod's into the alerts queue's block, which only prod has, neither touching the other environment's var file; each environment must then plan no change, and drift find nothing to revert. `TestAWSEnvironmentsRegenerate` ([`environments_regenerate_test.go`](environments_regenerate_test.go)) imports the accounts, applies the merged root into each environment's workspace and adds prod's billing queue with `--incremental`. Then a scratch queue dev gets, added with `--incremental`, then deleted, must be reported no longer in the cloud at its address in the merged root, as dev's, by an `--incremental` import that leaves the merged root as it is. Once dev gets the alerts feature too and its reports queue loses its tags, `--regenerate`, with dev's account split by tags between dev and an empty qa, must give the merged root a `moved` block for prod's alerts, which no `count` gates now, and a `removed` block for the reports queue, which the shared root of dev's account imports. Applied in order, the merged root as each environment, then the shared root, every plan must have no changes. Then, with the merged root's `moves.tf` deleted as its README says, `--regenerate` with a `--layout` of a root per service must put everything the merged root and the shared root have in roots of each service, which merge into `aws/sqs/us-east-1` and `aws/sns/us-east-1` and import it: the old merged root must keep only `removed` blocks, with what each environment plans it with and none of its code or import IDs, and its README say where each resource goes. Applied in order, the old roots first, every plan must have no changes.

[`TestAWSEnvironmentsData`](environments_aws_test.go) runs on the same runner. It creates [`testdata/aws-environments-data`](testdata/aws-environments-data/main.tf) in two more accounts of their own, `717171717171` and `818181818181`, mapped to `dev` and `prod`, and imports their IAM at once, with a [catalogue overlay](testdata/catalogue/environments-data/aws.yaml) that leaves prod's alerts policy out: the role prod alone has reads it through a data source only prod's root has. The merged root, `aws/global`, must count that data source with the feature's `deploy_` variable, `count = var.deploy_<feature> ? 1 : 0`, refer to its instance, and, planned as each environment, import what the environment has and change nothing.

The options tests ([`options_test.go`](options_test.go) and [`options_input_test.go`](options_input_test.go)) run the command-line options on [`testdata/aws-options`](testdata/aws-options/main.tf), created in an account of its own (`444444444444`), and check each option's effect on the output, with every root planning as imports with no changes:

- `TestAWSOptionsLayout`: `--layout={out}/{provider}/{account}/{region}/{service}/` puts each service's resources in a root of its own, the subnet and security group read the VPC of another root through a data source, and the default `--modules` (registry) makes the buckets calls of the curated s3-bucket module at its tested version, and the roles calls of one generated local module.
- `TestAWSOptionsModules`: `--modules=none` writes no module call or module, `--modules=local` only generated local modules, and `--modules=latest-untested` calls the s3-bucket module's newest release. `infraharvest verify` passes on the `none` output, then exits with 1 once a generated file says another queue retention than the queue has.
- `TestAWSOptionsReport`: `--format json` prints the report on stdout as one JSON document, which `infraharvest report --format json` prints again, as `infraharvest report` prints `report.md`; `--report-tags` counts by a tag; `--list-parallel=1` lists one service at a time; a `--catalogue` overlay ([`testdata/catalogue/skip`](testdata/catalogue/skip/aws.yaml)) leaves a topic out; and a queue tagged `ManagedBy=Terraform` is left out, unless `--include-owned`.
- `TestAWSOptionsFilters`: `--services`, `--skip`, `--id`, `--tag` and `--where` keep exactly what they should: the EBS lister filters volumes by tag, and the SQS lister, which doesn't support tag filters, lists every queue.
- `TestAWSOptionsExitCodes`: an overlay ([`testdata/catalogue/gone`](testdata/catalogue/gone/aws.yaml)) whose topic import ID names no topic makes the import partial, exiting with 1, or 3 with `--allow-partial`; `--engine-timeout=1ms` fails the root.

CI runs them on two runners, `TestAWSOptionsLayout` and `TestAWSOptionsModules` on one, the others on the other; run in one process, they share the resources the first one creates.

Run them locally (needs Docker and Terraform >= 1.5; compiling uses a few GB of RAM):

```sh
docker compose -f e2e/compose.yaml up -d --wait
AWS_ENDPOINT_URL=http://localhost:4566 go test -tags e2e,minimal,aws -timeout 40m -v ./e2e/
docker compose -f e2e/compose.yaml down
```

Set `E2E_ENGINE=tofu` to run the same test with OpenTofu >= 1.6 (`--engine=tofu`). CI runs it with Terraform on every pull request, with OpenTofu every night on main (the Tests workflow's schedule, which runs the e2e jobs alone), and with both when the Tests workflow is run by hand (workflow_dispatch), because the output must work on both.

The tests don't delete what they create, so restart Floci (`down`, then `up`) before running them again.

The test uses test credentials and empty AWS config files, and refuses any `AWS_ENDPOINT_URL` other than localhost, so it never touches a real account.

To cover another service, add its resources to `testdata/aws/main.tf` and its infraharvest service name to `awsServices` in `aws_test.go`. Check Floci [supports the service](https://github.com/floci-io/floci/tree/main/docs/services) first.

Not covered yet:

- **Services Floci runs in Docker containers:** EC2 instances, Lambda, RDS and ElastiCache. The test would need the Docker socket mounted into Floci.
- **Lambda functions in general:** the generated configuration can't include the function code, so it doesn't validate until you add the package.

Floci gives a VPC's default security group no inbound rule, where AWS gives it one allowing all traffic from the group itself. Once the fixture is created, the tests give each default group that rule, so it is as AWS creates it: the default selection leaves it out, and the load balancer refers to the fixture VPC's default group through a data source. Without it, each default group would be imported as one configuration has changed.

An emulator doesn't enforce IAM permissions or reproduce every AWS API quirk, so this doesn't replace a check against a real account.

## Google Cloud (floci-gcp)

[`TestGoogleRoundTrip`](google_test.go) uses [floci-gcp](https://github.com/floci-io/floci-gcp), the Google Cloud member of the same emulator family:

1. Terraform creates the resources in [`testdata/google`](testdata/google/main.tf) in floci-gcp: a VPC network with a subnetwork and a firewall rule, a Cloud Storage bucket, a Pub/Sub topic with a subscription, a service account, grants in the project's IAM policy, and a KMS key ring with keys.
2. `infraharvest import google --all` imports them: with `--services='*'`, and again with `--env-tags`.
3. Terraform plans the generated configuration. Every resource must be an import with no changes, and every resource type created in step 1 must be imported.

Five more tests import the same resources, each through a flow the round trip doesn't take:

- `TestGoogleDrift` applies the roots, changes the bucket's `team` label through the Cloud Storage API, and checks `infraharvest drift` reports it as `kept`, traced through the bucket's module call (`source.module_path`), exiting with 4 with `--detailed-exitcode`, and, with `--accept`, writes it into the call's `labels`; the code must then plan no change but to the labels the provider keeps only in state, and drift, once the state is refreshed, find nothing. Only the bucket has labels, so labels several resources share are left to the AWS test.
- `TestGoogleSelection` runs `infraharvest discover google`, checks the selection file and the inventories it saves list what step 1 created, and leaves out a firewall rule named like a default network's ([`testdata/google-selection`](testdata/google-selection/main.tf)). It then edits the file to exclude the Pub/Sub subscription and include that rule, and imports with `--selection`: the import must import what the file includes and nothing else, with no changes.
- `TestGoogleIncremental` imports, creates a Pub/Sub topic ([`testdata/google-incremental`](testdata/google-incremental/main.tf)) and imports again with `--incremental`: the topic must be added to global's root, after the blocks of its type's file or in a new file, with nothing else changed, and the roots must still plan with no changes. Once the topic is deleted, another `--incremental` import must report it no longer in the cloud.
- `TestGoogleResume` imports again with `--resume` into a finished import's output, which must generate no root again.
- [`TestGoogleMCP`](mcp_google_test.go) drives the MCP server's `discover` and `import` tools as `TestAWSMCP` does, on the project in `global` through `cloud_asset`: with the Pub/Sub subscription excluded in the selection file, `import` must ask once, naming the project and the region, and import what the file includes and nothing else, with no changes.
- `TestGoogleReuseInventory` imports with `--reuse-inventory` after discover: the import must take the resources from the inventories discover saved and make none of the listing requests (searches and reads of the IAM policy) discover made.
- [`TestGoogleQuery`](query_google_test.go) takes a service enabled in the project ([`testdata/google-query`](testdata/google-query/main.tf)), `google_project_service`, a type no lister lists, through the `query` service as `TestAWSQuery` does, in the project's global resources. Its block goes in `project.tf`. floci-gcp serves no network firewall policies, which the [Google Cloud sandbox](#google-cloud-sandbox-a-real-project) lists instead.
- `TestGoogleRegenerateMoves` creates three buckets of its own ([`testdata/google-moves`](testdata/google-moves/main.tf)), which only its stand-in for Cloud Asset Inventory finds, imports them into one root per environment (`--env-tags=env`, `--modules=none`) and applies the `dev` root into a local state. It then gives one bucket the `prod` label, so another root, and imports again with `--regenerate`: `moves.tf` of the `dev` root must have a `removed` block, with `destroy = false`, for it; the gate, G8 included, must pass; the other buckets must keep their addresses; the `prod` root must import the bucket; both READMEs must name the other root; and `report.json` must list it under `departed`. Planned over the state the first apply left, the `dev` root must forget the bucket, creating and destroying nothing; applied, then the `prod` root applied, neither root may plan any change. A bucket's name is its ID, so no bucket gets another address: `moved` blocks are left to the AWS test.
- `TestGoogleRegenerateHalfDone` hands a bucket over as `TestGoogleRegenerateMoves` does, with buckets of its own (the fixture's `prefix`), but the `dev` root can't be written while the import runs with `--regenerate` and `--allow-partial`, so generating it again fails after the `prod` root imported the bucket. `report.json` must list the handover under `incomplete_handovers`, with the `dev` root as the one that failed and a warning to generate it again with `--regenerate`, and `report.md` under Handovers not finished; the `dev` root must have no `moves.tf`, so its state keeps the bucket. Imported again with `--regenerate`, the handover must finish with the same checks as `TestGoogleRegenerateMoves`, the roots applied in order planning no change.

[`TestGoogleEnvironments`](environments_google_test.go) runs on a runner of its own, as it changes the estate. It creates [`testdata/google-environments`](testdata/google-environments/main.tf), a bucket of `dev` and one of `prod` in the project, each with an `owner` label of its own, which a configuration file's environments tell apart by their `env` label, and takes them through the whole chain on one merged root, imported with `--modules=none` so that each bucket is a resource of the root. Their roots must merge into `google/global`, with each environment's owner in its var file, which must plan as each environment with no changes. Each environment applies the merged root into its workspace. Then, as from a fresh checkout of the output, with `.infraharvest/`, `imports.tf` and each environment's `imports.tfvars` deleted, dev gets a Pub/Sub topic labelled as dev's: `--incremental` with `--managed-state` on the workspaces' states must add it into the merged root as dev's, and nothing else; in its workspace, dev must import the topic alone and prod nothing. Applied into dev's workspace, the topic is deleted out of band as prod gets a reports bucket: from a fresh checkout again, with `.infraharvest/` deleted, one `--incremental` import must add the bucket into the merged root as prod's and report the topic no longer in the cloud, as dev's, at its address in the merged root, which keeps it, with dev's import of it, and every other address; Cloud Asset Inventory lists every topic, so it counts as gone. The topic is then created again, and each environment applies the merged root into its workspace. Once dev's bucket gets another owner label out of band, `drift --environment=dev` must report it as dev's, `kept`, and, accepted, write it into `vars/dev/terraform.tfvars` alone, with no code written, and `drift --environment=prod` must find nothing. As [Drift](../docs/drift.md#tags-several-resources-share) says, the next Google plan of a label accepted at a resource may still show the label added to the resource's `labels`, which changes only the state: each environment's plan must change nothing else, applied it must change nothing, and drift then find nothing to revert. `--regenerate` with nothing changed must keep every address, with no `moves.tf`, and each workspace plan with no changes. Last, the topic loses its `env` label, so it is in no environment: `--regenerate` must give the merged root a `removed` block for it, which the project's shared root, under `envs/shared/`, imports. Applied in order, the merged root as each environment, then the shared root, every plan must have no changes.

CI runs the round trip, `TestGoogleIncremental`, which adds to what the others import, `TestGoogleDrift`, which changes it, and `TestGoogleEnvironments`, on runners of their own, and the others on a fifth; run in one process, they share the resources the first one creates.

## AWS sandbox (a real account)

[`TestSandboxAWS`](sandbox_aws_test.go) runs against a real AWS account, for what the emulators can't show: VPCs with NAT gateways, an EC2 instance, a Lambda function, REST and HTTP APIs, WAF and CloudFront, resources in two regions, and the attributes AWS returns that Floci doesn't. The `sandbox-aws` workflow runs it, started by hand (`gh workflow run sandbox-aws.yml -f engine=terraform`, the main estate by default), from a branch of this repository, with no approval step (the `sandbox` environment allows no other branches):

1. It signs in to two roles through GitHub's OpenID Connect, with no stored keys: `AWS_FIXTURE_ROLE_ARN` creates and destroys the estate, and `AWS_READONLY_ROLE_ARN`, the [read-only template](../docs/permissions.md#aws) (ReadOnlyAccess and the data-read deny), imports it, as a user would. Both are variables of the environment, with `AWS_REGION`, `AWS_BOUNDARY_POLICY_ARN` (the permissions boundary of the roles the estate creates) and, optionally, `AWS_SECOND_REGION` (by default `eu-west-1`). A one-time bootstrap creates them (see [Setting up the AWS sandbox](#setting-up-the-aws-sandbox)). A run stops at its first step when `AWS_REGION`, either role or the boundary is unset, rather than minutes into the apply.
2. Terraform creates [`testdata/sandbox/aws`](testdata/sandbox/aws/main.tf) as the fixture role, every resource tagged `infraharvest-sandbox=<engine>` and `infraharvest-sandbox-run=<run id>` (the `run_id` variable, from `TF_VAR_run_id`): most of it in `AWS_REGION`, a queue and a parameter in the second region, through a provider alias, and a DynamoDB global table in `AWS_REGION` with a replica in the second region, which gets the table's tags.
3. `infraharvest import aws --all --regions=<region>,<second region>` imports the resources of those services as the read-only role, and the generated configuration must plan as imports with no changes. Unlike on Floci, no attribute is excused as an emulator gap. Each resource the estate created must be imported by its ID, as the plan reads it, so a leftover of an earlier run, or a resource AWS made, can't stand in for one the import missed; only role policy attachments, whose IDs differ between a create and an import, are counted. Each region gets a root of its own with its own resources, and the global ones (IAM, Route 53, CloudFront) are imported once, into the global root. Both VPCs become calls of the vpc module: one with a single NAT gateway, one with a NAT gateway in each of two zones (`one_nat_gateway_per_az`). The global table must be imported once, as one `aws_dynamodb_table` in the root of the first of the two regions by name, with a `replica` block for the other region alone, and left out of the other region's root as a replica.
4. The test interrupts that import, which goes one region at a time, as Ctrl-C would, when it starts on the second region's root, the last, and runs it again with `--resume` and both regions at once (`--parallel=2`): the log must show the two regions listing at the same time, the roots generated before the interrupt stay as they were, and the interrupted one comes out as it does when the test generates it again from nothing, one region at a time. So the output doesn't depend on `--parallel`, at no more calls to AWS than the resume makes anyway.
5. It takes the estate's metric filter (`aws_cloudwatch_log_metric_filter`), a type no lister lists, which the services above leave out, through the `query` service as the read-only role, as [`TestAWSQuery`](#aws-floci) does on Floci: listed through Terraform's list resources, by its identity, refused with `--engine=tofu`, imported alone (`--id`) into `logs.tf` by an import block with its identity, and planned as one import with no changes.
6. It then adds a log group to the estate (`-var extra=true`) and imports again with `--incremental`: only the log group is added to its region's root, after the blocks of its type's file or in a new file, nothing else changes, and every root still plans with no changes, importing each resource once.
7. It applies the root the log group went to, in a copy of the output, keeping its state, as the read-only role: the apply only imports. It then gives the log group a `Name` tag (`-var extra_name=…`), which gives it another address, and imports again with `--regenerate`. The root's `moves.tf` must move the log group, and, planned over the state the first apply left, the root must show it as moved, creating and destroying nothing. It gives the log group another `Name` tag out of band, as the fixture role, and runs `infraharvest drift --root=<that root>` on the applied copy as the read-only role: the tag must be reported as `kept`, `--detailed-exitcode` must exit with 4, and the code must stay as it was. With `--accept 'type=aws_cloudwatch_log_group'`, the tag must be written into the code, which must then plan no change. Only the log group changes in the cloud.
8. The estate is destroyed, by the test and again by the workflow, with fresh credentials, whatever happened; the workflow fails if anything is left in its state, which the log group is in too. Last, whatever happened, it sweeps the regions for what still carries the run's `infraharvest-sandbox-run` tag and deletes all of it, without final snapshots, in the order its dependencies allow ([`sandbox-aws-sweep.sh`](../.github/scripts/sandbox-aws-sweep.sh)): Route 53 zones, with their records, and CloudFront distributions, which it disables first and deletes once they are deployed disabled; then what runs or holds the network (instances, NAT gateways, load balancers, ECS services, databases and clusters); then what uses nothing else (functions, APIs, state machines, tables, after their replicas in other regions, streams, queues, topics, buckets, secrets, log groups, alarms, rules, the `/ih-sbx-` SSM parameters, task definitions and stacks; KMS keys are scheduled for deletion after the shortest wait, 7 days); then target groups, WAF web ACLs and IP sets, Elastic IPs and the databases' subnet and parameter groups; then the network itself, a few rounds over, as the interfaces load balancers and NAT gateways leave go a few minutes after them; and last the `ih-sbx-` IAM roles that carry a run tag, with their instance profiles. It touches nothing without the run's tag but the aliases, instance profiles and log groups named `ih-sbx-` of what it deletes, and covers the other estates too. What still carries the tag is reported as a warning: the Tagging API lists deleted resources for a while. A cancelled job gets only five minutes for that, and one that times out or loses its runner runs no more steps, so when the round trip doesn't succeed, a clean-up job of its own, with its full timeout, runs the sweep again. It belongs to the `sandbox` environment too and needs no approval, after a cancel as well; the next run waits for it. Should that clean-up fail, the next run finds what is left before it creates anything, as the estate's names are the same each run, and sweeps it first. The state stays on the round trip's runner and is never uploaded, so the clean-up job goes by tag or name alone. The import's report (`report.md` and `report.json`) is uploaded as an artifact (`sandbox-aws-<estate>-<engine>`), kept for 7 days. The generated configuration is uploaded only encrypted (see [The generated configuration](#the-generated-configuration)), as the artifacts of a public repository are public.

The import covers the whole of both regions, so the account should hold nothing but the sandbox estate: anything else is imported and checked too, and the incremental import counts on nothing else changing while it runs. So only one run, of either engine and either estate, runs at a time. The [`sandbox-leftovers`](../.github/workflows/sandbox-leftovers.yml) workflow, which lists what runs left in each cloud, waits for the run in progress too when it is started with `delete`, as its sweep deletes what any run tagged. One run lasts under an hour and costs well under a dollar: three NAT gateways (about $0.045 an hour each, with their Elastic IPs), a load balancer and a `t4g.nano` instance.

### Setting up the AWS sandbox

[`testdata/sandbox/aws-bootstrap`](testdata/sandbox/aws-bootstrap/main.tf) creates what the workflow needs, once: the two roles, trusting the GitHub tokens of the `sandbox` environment alone (the subject `repo:IgnatG@6107088/infraharvest@1420684118:environment:sandbox`, the repository's immutable subject for it, with no wildcard), and the permissions boundary of the estates' roles. The read-only role is `permissions/aws`, the template users apply: ReadOnlyAccess without the reads of data, so the import is checked with the deny in place. The fixture role is PowerUserAccess, which leaves IAM out, and may manage only the roles and instance profiles named `ih-sbx-*`, which the estates create, and create a role only with the boundary (`infraharvest-sandbox-boundary`: everything PowerUserAccess allows, nothing in IAM but service-linked roles), which the estates set on every role (`permissions_boundary_arn`, from the environment's `AWS_BOUNDARY_POLICY_ARN`). So a run can't change the two roles, the OIDC provider or any other role of the account, nor sign in to a role, nor make a role that can do more than the fixture role.

```sh
git clone https://github.com/IgnatG/infraharvest.git
cd infraharvest/e2e/testdata/sandbox/aws-bootstrap
terraform init
terraform apply
terraform output -raw gh_commands
```

Apply it as an administrator of the account. `-var region=<region>` sets another region than `eu-west-2`, and `-var create_github_oidc_provider=true` creates the account's GitHub OIDC provider, which an account that never signed in to GitHub has none of. An account that already has the roles (the sandbox's was made by hand) imports them first, then applies, which replaces their policies:

```sh
terraform import aws_iam_role.fixture infraharvest-ci-fixture
terraform import aws_iam_role_policy_attachment.fixture_power_user infraharvest-ci-fixture/arn:aws:iam::aws:policy/PowerUserAccess
terraform import aws_iam_role_policy.fixture_iam infraharvest-ci-fixture:fixture-iam
terraform import module.readonly.aws_iam_role.readonly infraharvest-ci-readonly
terraform import module.readonly.aws_iam_role_policy_attachment.read_only_access infraharvest-ci-readonly/arn:aws:iam::aws:policy/ReadOnlyAccess
```

The last command prints the `gh variable set` commands that set the environment's variables, `AWS_BOUNDARY_POLICY_ARN` among them. Run them where `gh` is signed in as an administrator of the repository, then start a run:

```sh

1. 3. `infraharvest verify --environment=<env>`, as each environment's read-only account, must pass every check of the merged root as that environment.
4. `prd`'s `owner` label changes out of band, as the second fixture account: `drift --environment=prod`, as prod's read-only account, must report it as prod's, `kept`, exiting with 4, and `drift --environment=dev`, as dev's, must find nothing.

## Applying the generated roots

Each sandbox test also does what a team does with the output. It copies the output directory without any state, then for each generated root:

1. Runs `terraform init`.
2. Runs `terraform apply` as the read-only identity that imported. The apply only imports: every resource goes into a new local state, and nothing in the cloud changes, so read access is all it needs. Google Cloud is the exception: after an import, the Google provider updates the labels of each labelled resource in place, to the values it already has, which needs the right to update it. So the Google test applies as the fixture account, as a team applies with its deployment identity, and the bootstrap gives the fixture `roles/viewer` and `roles/iam.securityReviewer` to read what the roots import.
3. Runs `terraform plan` again, which must find nothing to import or change.

The test fails if the apply leaves nothing in state, or if anything is still planned after it. The state stays on the runner and goes with it.

## The generated configuration

When the repository variable `SANDBOX_OUTPUT_KEY` holds an OpenPGP public key, each sandbox run encrypts its output directory to that key and uploads it as the artifact `sandbox-<cloud>-...-output`, kept for 7 days. The archive leaves out `.terraform` directories, state and variables files. Only the holder of the private key can read it:

```sh
gh run download <run-id> -n sandbox-aws-main-terraform-output
gpg --decrypt output.tar.gz.gpg | tar -xz -C <directory>
```

Each artifact is named `sandbox-<cloud>-<estate>-<engine>-output`, and `gh run view <run-id>` lists a run's artifacts. On Windows, Git Bash has `gpg` and `tar`; Gpg4win's `gpg` works too if the key is in its keyring.

Without the variable, only the report is kept.

### The key

The maintainer holds the only private key; `SANDBOX_OUTPUT_KEY` holds its public half, ASCII-armoured, as a repository variable (not a secret: it is public anyway). Show which key the variable holds, and which key an archive was encrypted to:

```sh
gh variable get SANDBOX_OUTPUT_KEY | gpg --show-keys
gpg --list-packets output.tar.gz.gpg | grep pubkey
```

Back the private key up when it is made, and again whenever it changes, somewhere other than the machine that holds it, such as a password manager:

```sh
gpg --export-secret-keys --armor <fingerprint> > sandbox-output-key.asc
```

Restore it on another machine with `gpg --import sandbox-output-key.asc`.

To replace the key, when it is lost or should no longer be trusted, make a new one with an encryption subkey, set the variable to its public half and back the private one up:

```sh
gpg --quick-generate-key "infraharvest sandbox output <sandbox-output@infraharvest.invalid>" ed25519 cert never
gpg --quick-add-key <fingerprint> cv25519 encr never
gpg --export --armor <fingerprint> | gh variable set SANDBOX_OUTPUT_KEY
```

A lost key costs only the archives encrypted to it, which expire after 7 days anyway: nothing in them is kept anywhere else, and the next run of each estate writes them again, to the new key.
